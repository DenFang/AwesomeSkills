# Color picker UX: format, memory, live contrast, alpha preview, palette output

**Hook:** One pick recolours the whole interface (button, toggle, progress bar, badge), so the picker should help you make a good decision, not just expose a gradient and a hue slider.

## Main rule
A color picker should offer a perceptual format (OKLCH) next to hex, remember recent and saved picks, show the contrast ratio of the pick against its real pairing while you drag, preview alpha over a checkerboard on both a light and a dark surface, and be able to expand one pick into a full tint/shade scale of tokens.

## Before / after
- **Hex-only vs OKLCH.** Bad: only a hex field; to get a lighter variant you guess new hex digits. Good: OKLCH sliders where moving Lightness alone (0.62 to 0.75) gives a lighter version of the same colour with the same perceived saturation and hue. Why: OKLCH axes map to perception (lightness, colourfulness, hue), so one-axis edits are predictable; hex/RGB channels are device encodings.
- **No memory vs recent + saved.** Bad: each session starts blank and you re-hunt a colour you used a minute ago. Good: a "Recent" row (last 5 picks) and a saved brand palette (4 colours); one tap restores a pick with a confirmation. Why: recognition over recall, fewer repeated steps.
- **Contrast checked in review vs at pick time.** Bad: a failing pair is found later in QA. Good: a live ratio badge next to a real preview (button with label) updates while dragging and flips from fail to pass at 4.5:1. Why: feedback at the moment of decision prevents the bad value from ever being committed.
- **Alpha on a light canvas vs alpha on both surfaces.** Bad: translucent colour previewed only on a light canvas, where it reads as a soft pastel. Good: checkerboard alpha track plus side-by-side "On light" and "On dark" previews; at about 39% the same fill is pastel on light and nearly invisible on dark. Why: alpha colours are composited, so their visible colour and contrast depend on the background.
- **Single value vs scale.** Bad: the picker outputs one value. Good: it generates a 10-step ramp (50 to 900) from one hue so the pick becomes a token system. Why: consistent tints/shades instead of ad-hoc variants.

## Do
- Show OKLCH (L, C, H) alongside hex; keep hex copyable for code.
- Persist the last 5 picks and allow named saved palettes.
- Preview the colour inside a real component and show the live contrast ratio with pass/fail against 3:1, 4.5:1 and 7:1.
- Draw a checkerboard behind alpha and preview on both a light and a dark surface.
- Offer "generate scale" output as named steps (50...900).

## Don't
- Don't ship a bare gradient square plus hue slider as the whole picker.
- Don't preview transparency only on a light canvas.
- Don't defer contrast checking to design review.

## Voice-over summary
- A colour pick ripples through the whole UI.
- Hex is for machines; OKLCH reads like a human (lightness, chroma, hue): change one number, get a predictable shade.
- A picker without memory wastes time: keep recent swatches and saved palettes, last five picks one tap away.
- Check contrast at pick time, not in review; a live ratio badge flips from fail to pass.
- Transparency lies on a light canvas; a checkerboard and light/dark previews tell the truth.
- One pick can generate tints and shades: "Ten tokens. One decision."

## Notes for the skill
- Contrast thresholds (WCAG 2.x): 4.5:1 normal text, 3:1 large text (24px regular or ~18.66px bold) and non-text UI parts/focus indicators, 7:1 AAA. The demo badge passes at 4.5:1 for a button label, which is correct for normal-size text. Show the ratio as a number plus a text label (FAIL / AA / AAA), not colour alone.
- Compute contrast on the composited colour when alpha < 1 (blend over the actual surface), and re-check per theme.
- OKLCH "predictable" is mostly true for lightness; raising chroma can leave the sRGB/P3 gamut, so clamp or gamut-map and indicate when the value is out of gamut. CSS: `oklch(L C H / a)`, `color-mix(in oklch, ...)` and relative colour syntax can derive steps.
- The 10-step ramp shown appears to be a hand-tuned framework palette rather than an algorithmic output; real generators should vary chroma along the ramp (lower chroma at extremes) and verify contrast of text steps.
- Accessibility of the picker itself: the 2D area and sliders need keyboard support (arrow keys, `role="slider"` with `aria-valuenow`/`aria-valuetext`, or native `input type=range`), and a typed text field must always be available. Native `<input type="color">` is a reasonable baseline.
- Recent list: dedupe, most-recent-first, cap at 5; persist per user/project.
