# Tree view: five rules for a deep folder tree

**Caption:** Four folders deep and still not lost: five tree rules (ends with a plug for the author's plugin).
**Hook:** Four levels deep in a file tree, where are you?

## Main rule
Indent each level by 16px and drop a thin guide line from every open folder; open and close by rotating one chevron 90 degrees (180 ms) instead of swapping icons; make the whole tree operable with arrow keys (Right opens, Left closes, Up / Down move); fetch a large folder's children only on open, with skeleton rows in place while the rest of the tree stays usable; while dragging, a closed folder springs open after a 600 ms hover.

## Before / after
- **Indent + guides (0:03-0:12):** Before: "8px, no guides", nested levels differ by a small gap, so depth must be judged by counting tiny offsets. After: "16px + guides", each level shifts by 16px and a thin vertical line runs from every open folder down its children; hovering a row highlights the guide of its parent. Why: a continuous line is a single visual object the eye can follow (Gestalt continuity / common region); at four levels, gaps alone are too small to compare, the line shows which folder a file belongs to.
- **Rotating chevron (0:13-0:20):** Before: icon swap between two glyphs (right chevron component vs down chevron component), "two glyphs, the eye jumps". After: one chevron rotates 90 degrees over 180 ms; the folder icon never changes; "same glyph, eye stays put". Why: rotation is perceived as the same object changing state (object constancy), and the motion shows direction (pointing at the revealed children); a glyph swap is a discontinuity that draws a saccade.
- **Arrow keys (0:21-0:30):** focus ring moves app → billing (↓), billing opens (→) showing invoices, BillingPage.tsx, plans.ts, closes (←), ↑ previous row, ↓ next row; tag "mouse: not needed". Why: trees are long and deep; keyboard traversal is faster for power users and required for accessibility.
- **Lazy children (0:31-0:38):** Before ("tree locked"): one spinner over the whole panel, "every click waits for 1,284 items". After: only node_modules shows "fetching" with three skeleton rows under it; meanwhile "components" can still be hovered ("still usable"); then the folder shows "loaded" with @remix-run, react, zod. Why: scoping the loading state to the node that is loading keeps the rest of the UI interactive and shows exactly where content will appear (skeletons reserve space, so rows below don't jump twice).
- **Spring-loaded folders (0:39-0:47):** a file (InvoiceRow.tsx, "move") is dragged onto closed "components": a progress ring fills (500ms readout), at 600 ms the folder opens, the same happens on the nested "invoices" folder ("600ms · open"), the file is dropped and the row flashes "moved". Why: the user can reach a deep target without releasing the drag to open folders manually; the delay prevents folders from opening when the pointer merely passes over them.

## Do
- Indent 16px per level and draw a 1px guide line under each open folder; highlight the guide of the hovered or focused branch.
- Use a single chevron that rotates 90 degrees (closed: pointing right, open: pointing down) with a short transition (about 180 ms); keep the folder icon unchanged.
- Support full keyboard navigation: Right opens a closed folder, Left closes an open one, Up / Down move between visible rows.
- Load children of large folders on first expand; show skeleton rows inside that folder only and keep the rest of the tree interactive.
- During drag and drop, open a hovered closed folder after about 600 ms, with a visible timer cue; cancel if the pointer leaves.

## Don't
- Don't rely on tiny (8px) indents without guide lines for deep trees.
- Don't swap two different icons for collapsed / expanded, and don't swap the folder icon.
- Don't make the tree mouse-only.
- Don't block the whole panel with one spinner while one folder loads.
- Don't open folders instantly on drag-over (accidental expansion) or not at all (forces the user to drop, open, drag again).

## Notes for the skill
- Semantics (WAI-ARIA APG Tree View): container `role="tree"` with `aria-label`; items `role="treeitem"`; children wrapped in `role="group"`; `aria-expanded` only on items that have children (not on files); `aria-selected` for selection; one tab stop with roving `tabindex`. For lazily loaded or virtualised trees also set `aria-level`, `aria-setsize`, `aria-posinset`, and `aria-busy="true"` on the loading group.
- Full APG keyboard model is richer than the reel's: Right on a closed node opens it, on an open node moves to its first child; Left on an open node closes it, on a child or closed node moves focus to the parent; Up / Down move between visible nodes; Home / End jump to first / last; Enter activates (opens file); type-ahead jumps by first letters; `*` expands all siblings (optional).
- CSS: indent via `padding-inline-start: calc(var(--level) * 16px)` (logical property, so it mirrors in RTL, where the closed chevron should point left); guides as a 1px pseudo-element or border on the group at the parent's chevron x-position, in a muted border colour, with the active branch in a stronger colour. Very deep trees may need horizontal scroll or a cap on indentation width.
- Chevron: `transition: rotate 180ms ease-out` (or `transform`); `[aria-expanded="true"] > .chevron { rotate: 90deg }`. Under `prefers-reduced-motion: reduce` switch instantly; the state is still conveyed by the final angle.
- Chevron and row targets: the chevron hit area should be the whole row or at least 24 x 24 CSS px (WCAG 2.5.8); focus ring visible with at least 3:1 contrast (WCAG 2.4.7 / 1.4.11), as in the reel's outlined focused row.
- Lazy load: show skeletons only after a short delay (about 150-300 ms) to avoid flashes on fast responses; handle errors inline in the folder ("Couldn't load, Retry") rather than collapsing silently; announce completion politely if it took long.
- Spring-loaded folders: 600 ms is a reasonable delay (macOS Finder uses a similar user-adjustable delay); show progress on the target, reset the timer when the pointer leaves, and optionally auto-collapse folders opened by the drag if the drop happens elsewhere. Dragging needs a non-drag alternative (WCAG 2.5.7 Dragging Movements): provide "Move to..." in a context menu or cut / paste with the keyboard.
- The reel's claim that arrow keys mean "you never reach for the mouse" holds only if every action (rename, delete, create, move) also has a keyboard path; tree navigation alone is not full keyboard operability (WCAG 2.1.1).
