# Bulk actions: selection is a system

**Caption:** not captured yet
**Hook:** Ticking the header checkbox silently pulls in all 247 rows while only 6 are visible; bulk selection has to be designed as a whole system, not a single checkbox.

## Main rule
Treat bulk selection as a stateful system: a tri-state header checkbox (empty / partial / checked), an explicit count for every scope ("Select all 247 matching"), selection stored as ids in app state so it survives shift-ranges, paging and filtering, and destructive bulk actions that echo the count, run immediately and offer a timed undo instead of a confirm modal.

## Before / after
1. **Two-state vs tri-state header checkbox.** Bad: the header box is only on/off, so after picking some rows the header gives no sign that a partial selection exists, and users lose track of what they picked. Good: the header shows a dash (indeterminate) when 2 of 5 rows are selected; clicking the dash selects all rows, never clears. Why: the header becomes a summary of selection state; making partial resolve to "select all" gives one predictable direction and avoids accidentally wiping a careful manual selection.
2. **Bare "all" vs a named count.** Bad: header select-all grabs only the 6 rows on screen while the table holds 247, and the user cannot tell which scope they are about to act on. Good: the bar says "6 selected" with a link "Select all 247 matching"; after clicking, the count ticks to 247 and a "Clear selection" action appears. Why: an explicit number removes scope ambiguity before a bulk action; the user sees exactly what will be affected.
3. **Static count vs live count under filters.** Bad: a label that keeps saying 247 after a filter is applied. Good: choosing "Plan: Pro" re-reads the count to 96 (both "96 selected" and "matching = 96") and the non-matching rows dim. Why: people must act on the real current set; a stale number misleads destructive actions.
4. **DOM-bound selection vs state-bound selection.** Bad: selection is stored on the visible rows, so changing page kills it. Good: shift-click on the last row selects the whole range (4 rows) and a `selectedIds` store keeps those ids when the user goes to page 2 with different rows. Why: shift-range is a desktop expectation; storing ids in app state decouples selection from rendering, so paging, virtualization and filtering do not lose it.
5. **Confirm modal vs undo.** Bad: "Are you sure? This will delete 247 members" with Cancel / Confirm, labelled "friction without recovery" and struck through. Good: the button reads "Delete 247", the delete runs immediately, the table shows an empty state "No members left in this view · 247 removed a moment ago", and a toast "247 members deleted · recoverable for ten seconds" with an Undo button and a draining 10 s countdown ring. Why: confirm dialogs become reflexive clicks and still offer no recovery after the mistake; echoing the count gives informed intent up front and undo makes the action reversible ("reversible beats careful").

## Do
- Give the header checkbox three states and render the dash for any partial selection.
- Make clicking the partial (dash) header select every row.
- After a page-level select-all, offer an explicit escalation "Select all N matching" with the real number.
- Recompute and display the count live whenever filters or search change the matching set.
- Support shift-click to select a contiguous range from the last clicked row.
- Store selection as a set of ids in application state so it survives paging, filtering and re-rendering.
- Put the count inside the destructive button label ("Delete 247") and in the result toast ("247 members deleted").
- Run reversible bulk deletes immediately and show an undo toast with a visible countdown (10 s in the video).
- Provide a "Clear selection" action in the selection bar.
- Show an empty state after the delete that names what happened ("247 removed a moment ago").

## Don't
- Ship a two-state header checkbox without the indeterminate dash.
- Let the partial header click clear the selection.
- Label bulk scope with a vague "all" that hides how many rows will be touched.
- Keep selection in DOM checkbox state, where changing page silently resets it.
- Put an "Are you sure?" modal in front of a bulk delete when you can offer undo instead.

## Voice-over summary
- Ticking the header box quietly brings all 247 rows along; the header checkbox needs three states: checked, empty and partial.
- Without the partial state users lose track of what they picked; clicking a partial box should select everything and never clear.
- Select-all that only grabs the 6 visible rows out of 247 must say the number out loud ("Select all 247 matching"), and the label must update live when a filter changes it.
- Shift-click range selection is a desktop expectation, and selection must live in app state so it does not die on page change.
- A 247-row delete does not need a confirm modal: echo the count in the button, run it, then offer undo for 10 seconds; "Reversible beats careful."

## Notes for the skill
- Native checkbox: set `input.indeterminate = true` for partial (it is a DOM property, not an attribute); for custom checkboxes use `role="checkbox"` with `aria-checked="mixed"`. The WAI-ARIA APG mixed checkbox pattern cycles mixed → checked → unchecked; the "partial resolves to select-all" rule matches common table practice (Gmail, GitHub), but document it consistently.
- Model selection as `selectedIds: Set<id>` plus, for "select all matching", a query-scoped flag (`allMatching: true, excludedIds`), so you do not need to load all 247 ids client-side and so the selection can be re-evaluated when the filter changes.
- Decide explicitly what a filter change does to an existing selection (keep ids that still match and show the new count, as in the video); never act on hidden rows that no longer match without saying so.
- Shift-click range: remember an anchor row (last clicked), select the inclusive range between anchor and target in current sort order; add keyboard equivalents (Shift+Space / Shift+Arrow in grids per APG grid pattern).
- Announce count changes with a polite live region (`aria-live="polite"`) on the selection bar ("6 selected", "247 selected").
- Animated count tick-up is decorative; under `prefers-reduced-motion: reduce` jump straight to the final number.
- Undo instead of confirm only works if the delete is actually reversible (soft delete or deferred commit until the window closes). For irreversible actions (permanent purge, external side effects) a confirm step with the count is still appropriate.
- A 10 s undo toast must not auto-dismiss while hovered or focused, and the Undo button must be keyboard reachable; WCAG 2.2.1 (Timing Adjustable) applies to time limits, so keep the undo also reachable elsewhere (e.g. a "Recently deleted" view) for users who need more time.
- The danger colour on "Delete N" should be reserved for destructive actions; Undo uses the neutral/accent style, not danger.
