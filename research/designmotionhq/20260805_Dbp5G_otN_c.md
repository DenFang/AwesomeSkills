# The hover trap: actions that vanish on touch

**Caption:** Hover works on your laptop but is dead on mobile.
**Hook:** Hover a product card and its actions appear; tap the same card on a phone and nothing happens.

## Main rule
Never hide a primary action behind hover. Gate hover-reveal styles with `@media (hover: hover)`,
give every hover-revealed action a touch home (in the card, behind a swipe, or in a bottom sheet),
and pad icon buttons to a 44px hit area on coarse pointers while keeping the glyph about 20px.

## Before / after
1. **Desktop hover vs phone tap.** On desktop, hovering the card reveals Favorite / Compare / Quick
   view. On the phone the same tap shows a ripple and nothing else. Why: touch has no hover state,
   so anything that exists only on hover is unreachable.
2. **Sticky hover.** Bad: the browser emulates hover on the first tap; the actions appear and stay
   "frozen" (timer runs past 7 seconds with nobody hovering) until the user taps elsewhere; tap 1 is
   spent on the hover, only tap 2 is the click the user wanted. Why: mobile browsers map a tap to
   `:hover` + click; when hover changes content, the first tap is consumed and the hover state does
   not clear on its own.
3. **Device sniff vs pointer query.** Bad: `if (isMobile) hideActions()` (struck out). Good:
   `@media (hover: hover) { .card:hover .actions { opacity: 1; } }`. Why: the query asks the input
   device, not the device type, so a tablet with a mouse gets hover (hover: hover, pointer: fine)
   while a phone (hover: none, pointer: coarse) does not; user-agent sniffing gets hybrids wrong.
4. **Hidden actions vs a real home.** Bad: `.card .actions { opacity: 0 }` (labelled "gone on
   mobile"). Good options: 01 actions rendered in the card ("always there, zero discovery cost"), 02
   behind a swipe-left on the list row ("one gesture, one hidden layer"), 03 a bottom sheet listing
   Favorite / Compare / Quick view ("one tap opens every action"). Rule rows: extras such as compare
   and quick view may use hover; the primary action is always visible.
5. **20px vs 44px hit area.** Bad: comment/like/share icons with a 20px hit area; the thumb lands
   beside the heart and the tap is a no-op ("misses the thumb", "passed design review"). Good: the
   same 20px icons inside 44px padded boxes (dashed outlines show the hit area); the same thumb hits
   every time and the icon is still 20px. Why: a fingertip contact is much larger and less precise
   than a cursor; the hit area, not the glyph, decides success.

## Do
- Reveal only secondary extras on hover; keep every primary action visible and tappable.
- Wrap hover-reveal CSS in `@media (hover: hover)`.
- Use `@media (pointer: coarse)` to enlarge padding/hit areas for touch.
- Give hover-only actions a touch path: inline in the card, a swipe action, or a bottom sheet.
- Pad icon buttons to a 44px hit area and keep the visible icon around 20px.

## Don't
- Don't hide primary actions behind a hover state touch users cannot trigger.
- Don't detect touch by sniffing the user agent or screen width.
- Don't size the hit area to the 20px icon.

## Voice-over summary
- Hovering shows the card actions; tapping on touch does nothing, because touch has no hover and the browser fakes one.
- The first tap becomes a hover and freezes the actions until the user taps elsewhere.
- Guard hover with a `hover` media query, not a device sniff, so a tablet with a mouse still gets hover; pair it with `pointer: coarse` to grow targets.
- Anything hidden behind hover is gone on mobile; move it into the card, a swipe or a bottom sheet; hover reveals extras, never the primary action.
- Tap targets need 44px; a 20px icon passes review but misses the thumb, so pad the hit area and keep the icon small.

## Notes for the skill
- Pattern: actions visible by default; inside `@media (hover: hover) and (pointer: fine)` hide them and reveal on `.card:hover .actions, .card:focus-within .actions`. Without `:focus-within` the reel's CSS hides actions from keyboard users.
- `opacity: 0` alone leaves the hidden buttons focusable and tappable (invisible ghost targets). Hide with `visibility: hidden` / `pointer-events: none` as well, or render them only when shown.
- `(hover)`/`(pointer)` describe the primary input. For hybrids (touch laptops, tablets with optional mouse) consider `any-hover` / `any-pointer` and design so both paths work.
- Swipe actions are not discoverable and not keyboard/switch accessible; always pair a swipe with a visible alternative (overflow menu or long-press sheet). WCAG 2.5.1 Pointer Gestures requires a single-pointer alternative for path-based gestures.
- Target size: 44 × 44 CSS px matches Apple HIG (44pt) and WCAG 2.5.5 AAA; Material uses 48dp. The WCAG 2.2 AA minimum (2.5.8) is 24 × 24 CSS px or equivalent spacing, so "44px" is the recommended target, not the legal floor. Keep adjacent targets from overlapping when padding grows.
- `padding: 12px` gives 44px only if the icon box is exactly 20px; prefer `min-width/min-height: 44px` on the button or an expanded hit area via a pseudo-element so the layout does not shift.
- Content revealed on hover must also follow WCAG 1.4.13 (dismissible, hoverable, persistent) when it is tooltip-like.
- Sticky-hover detail: iOS Safari consumes the first tap only when the hover changes visible content; Android browsers keep `:hover` applied after a tap until another element is touched. Gating hover styles with the media query prevents both.
