# Dropdowns: five rules

**Caption:** Dropdown are essentials but needs to follow theses rules.
**Hook:** Your dropdown is broken; five rules separate a cheap one from a premium one.

## Main rule
A dropdown needs an obviously clickable trigger (caret, hover state, at least 44-48 px tall), collision-aware placement that flips upward near the viewport bottom, full keyboard support (arrows, Enter, Esc), a search field once the list passes about 10 items (virtualization above about 100), and an open animation of about 150 ms.

## Before / after
1. **Trigger (0:02-0:10).** Bad: a 30 px "Select option" box with a tiny filled triangle, low-contrast border, no hover feedback. Good: a taller "Account" trigger with a clear chevron caret, visible border and a hover state (border/glow in the accent colour when the pointer is over it). Why: affordance; the user must recognise it as interactive without trial, and a larger target is faster and easier to hit (Fitts's law, touch accuracy).
2. **Placement near the viewport edge (0:11-0:18).** Bad: the trigger sits at the bottom of a browser window, the menu opens downward and only "Option A" is visible, cut off by the window edge (badge "CLIPPED"). Good: the menu detects the edge and opens upward above the trigger, showing all five options A-E ("Detect edge. Flip the menu up."). Why: clipped options are unreachable or invisible; placement should be computed against available space, not fixed.
3. **Keyboard (0:18-0:25).** "Account menu" opens; Down arrow moves the highlight Dashboard -> Projects -> Settings, Enter selects Settings (the trigger label changes to "Settings"), Esc closes the menu. Caption "Every user. Every time." Why: keyboard and assistive-tech users cannot use a pointer-only widget.
4. **Long lists (0:26-0:33).** A "Search countries..." combobox lists Argentina, Australia, Austria...; typing "Fr" then "Fra" narrows the list to France. Caption "Filter beats scroll. Always." Why: recognition by typing is faster than visually scanning a long scroll list.
5. **Open speed (0:34-0:42).** Three identical menus open in a loop at 50 ms ("Too fast": it seems to pop with no perceptible transition), 150 ms ("Just right") and 500 ms ("Too slow": options still fading in while the others are done). Caption "Fast to feel instant. Smooth to feel real." Why: a short transition gives spatial continuity without making the user wait.

## Do
- Make the trigger at least 44 px tall (48 px for touch), with a visible caret and hover/focus states.
- Measure space below the trigger and flip the menu above it when it would overflow the viewport.
- Support Up/Down arrows to move, Enter to select, Esc to close (and return focus to the trigger).
- Add a filter/search input once a list has more than about 10 options; virtualize lists above about 100 items.
- Open the menu with a short transition, around 150 ms.

## Don't
- Don't ship a 30 px, low-contrast trigger with no hover feedback.
- Don't let a menu clip off the bottom of the viewport.
- Don't make the menu mouse-only.
- Don't force users to scroll-hunt through long lists.
- Don't animate the open for 500 ms, and don't skip a transition entirely.

## Voice-over summary
- Make the trigger obvious: a proper arrow, a hover state and a minimum 44 px click target, so users never wonder if it is clickable.
- When the dropdown reaches the bottom of the viewport it should open upward; never clip the last item.
- Keyboard navigation is not optional: arrows move, Enter selects, Escape closes.
- Past 10 items add search, because filtering beats scrolling; above 100 items virtualize the list.
- Animate in "under 150 milliseconds": fast enough to feel instant, slow enough to feel smooth; longer feels janky.

## Notes for the skill
- Numbers disagree slightly: voice says a 44 px minimum, screen and page say 48 px. Use 44 px as the floor (WCAG 2.5.5 AAA and Apple HIG 44 pt; WCAG 2.5.8 AA minimum is only 24 px) and 48 px for touch-first UI (Material 48 dp).
- Voice says "under 150 ms", screen says "Hit 150ms", page says "around 150ms" and lists 50 ms as too fast. Practical rule: 120-200 ms for the open, with the close shorter (about 100-150 ms) and a decelerating ease-out curve on open. The "50 ms feels cheap" claim is a taste judgement, not a usability fact; an instant open is acceptable and is the required behaviour under `prefers-reduced-motion: reduce`.
- Pick the right ARIA pattern: a value picker is a `combobox` + `listbox` (WAI-ARIA APG Select-Only Combobox, or editable combobox with search); an action list like "Account menu" is a menu button (`aria-haspopup="menu"`, `role="menu"` / `menuitem`). Set `aria-expanded` on the trigger and `aria-activedescendant` (or roving tabindex) for the highlighted option.
- Keyboard per APG also includes Home/End, type-ahead by first letter, Space/Enter/Alt+Down to open, and Tab closing the menu. Esc must return focus to the trigger.
- Searchable list: announce the result count with a polite live region, and show an explicit "No results" state.
- Edge flipping: use a positioning library (Floating UI `flip()` + `shift()`), or CSS anchor positioning with `position-try-fallbacks: flip-block`. Also constrain the menu's max-height to the available space and make it scrollable, since flipping alone fails when neither side has room.
- Native `<select>` already handles placement, keyboard and mobile pickers; build a custom one only when you need rich options or search.
- The hover state is not visible on touch devices, so make the trigger look interactive at rest (caret plus a border that has 3:1 contrast against its surroundings, WCAG 1.4.11). Add a visible `:focus-visible` style as well.
