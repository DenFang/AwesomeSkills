# Visual system

Tokens, type, colour roles, spacing, radius, elevation and hierarchy. These rules are palette-independent: they define relationships (how many colours, which role gets the accent, how surfaces step), never specific brand colours. Always use the project's own palette and tokens.

Severity: **P0** unreadable or inaccessible, **P1** inconsistent or confusing, **P2** polish.

---

### VIS-1 · Nothing is typed raw (P1)
**Applies to.** all styling (always check).
**Rule.** Every colour, size, space, radius, shadow, weight, duration, easing and z-index comes from a named token on a fixed scale. Layer tokens: **primitives** (raw values; value names such as a numbered 100 to 900 shade ramp per hue are fine here) → **semantic** (`--color-bg`, `--color-surface`, `--color-text-muted`, `--color-accent`, `--color-danger`) → **component** (`--button-bg`, `--card-padding`). Components read only semantic or component tokens, never primitives, so one changed primitive or repointed alias cascades everywhere. Name by role, not value (`--color-accent`, `--space-md`, not `--blue-500`, `--spacing-16`); a rebrand repoints semantic tokens to new primitives rather than mutating a primitive into a value its name no longer describes. Themes, including dark mode, swap the semantic layer and are re-checked for contrast (VIS-7); components never change. A shared component ships with its variants, sizes and every state (STA-1, INT-10), not just the default, and new screens reuse those variants: a third button style or a one-off card beside the shared one is drift, not a new decision.
**Detect.** Hex/rgb literals or px values inside components; components referencing primitive ramps (`var(--gray-200)`) directly; near-duplicate values on one scale (a 13 px gap next to 12, a 15 or 17 px font size next to 16); value names (hue, px) on tokens used for meaning; one-off variants (another primary button style) next to the shared component.
**Fix.** Snap stray values to the nearest step of the project's scale for that property (spacing 13 → 12, 17 → 16, 22 → 24 on a 4 px grid; type sizes snap to the type scale, VIS-4) and replace literals with tokens; pick the nearest colour token by perceived difference (OKLCH), not hex distance, and report every substitution. Before inventing tokens, extract the ones the project already encodes, in this order: theme config, CSS custom properties, token files, then the most reused component (its padding and radius are the de facto scale); derive a missing value from the values already in use. Write the result in one file every screen reads from; a value outside it is either snapped to a token or added as a documented extension with its reason, never typed in silently. If the project has no tokens at all, propose a minimal set before refactoring (see the "Missing design system" note in SKILL.md).

### VIS-2 · One spacing scale (P1)
**Applies to.** all spacing: padding, margin, gap, grid gutters.
**Rule.** One base unit (4 px or 8 px) and a short scale of selected steps (for example 4, 8, 12, 16, 24, 32, 48, 64 as step indices `--space-1` … `--space-8`, never pixel values in the name); every padding, margin and gap uses only these, with 2 px as the one documented exception for hairline or icon nudges. Random gaps (7, 11, 23) read as sloppy even when nobody can say why. A proportional scale (×1.5 or ×1.618: 8, 13, 21, 34, 55) is fine if it is the only scale; never mix its off-grid steps into a 4/8 px system, because one consistent scale matters more than which ratio it uses. Space between siblings belongs to the parent: `gap` on the flex or grid container, not a bottom margin on every child cancelled again with `:last-child` (for flowing prose a `.stack > * + *` margin is fine).
**Detect.** Many distinct spacing values; arbitrary Tailwind values (`p-[13px]`) for spacing; values not divisible by 4 in a 4 px system; `margin-bottom` on components reset with `:last-child { margin-bottom: 0 }`.

### VIS-3 · Spacing does the grouping (P1)
**Applies to.** every layout that groups items: toolbars, navigation and sidebar lists, forms, cards, page sections.
**Rule.** The gap inside a group is clearly smaller than the gap between groups, roughly 1:3 to 1:4 (for example 8 px between toolbar icons and 32 px between toolbar groups; 12 px between related fields and 40 px between form sections). Group toolbar, sidebar and nav items by function, and let the larger gap (plus a short group heading) draw the boundary before adding borders, boxes or dividers. A label sits closer to its own field than to the field above. Three kinds of white space: micro (padding inside elements), macro (between sections, often 40 px and more), active (deliberate emptiness around the one element that should pop, VIS-12). Cards and buttons that look cheap usually need more padding (about 24 px inside a card, 16 px between its elements) and more line-height in body text, not a redesign. On narrow screens shrink gaps by scale steps (card padding about 16 to 20 px on phones, 24 to 32 px wider) but keep the inside/between ratio. Layouts must survive user text-spacing overrides (line height 1.5, letter spacing 0.12em, WCAG 1.4.12), so never fix card or row heights around text.
**Detect.** Uniform gaps everywhere (an evenly spaced toolbar, a flat list of eight sidebar links); borders and dividers doing work spacing could do; label-to-input gap as large as the field-to-field gap; cramped padding (8 to 12 px on cards); body line-height near 1.1 to 1.2.
**Fix.** Give each visual group a semantic container as well (`fieldset` + `legend`, a `section` with a heading, `role="group"` inside `role="toolbar"`), so screen readers get the grouping that spacing shows.

### VIS-4 · Type: seven decisions made once (P1)
**Applies to.** all text styling.
**Rule.**
1. **Sizes**: about five steps from one base and one ratio. About 1.2 to 1.333 suits product UI (1.25: 13, 16, 20, 25, 31); 1.5 to 1.618 jumps fast (16, 26, 42, 68) and suits only marketing pages with few levels. Steps strictly increase with their names; set them in `rem`. Let display steps scale with one `clamp()` that keeps a rem term in the middle (`clamp(1.5rem, 1rem + 2.5vw, 3rem)`) instead of overriding the size at several breakpoints; a middle of pure `vw` ignores browser zoom (WCAG 1.4.4). Stop adding sizes.
2. **Inks**: three text roles (primary, secondary, muted) rank text within a line; size ranks between blocks.
3. **Weights**: two or three (for example 400 to read, 600 to scan, 700 to 800 for display). Keep small text at 400 or heavier, especially light on dark: a 300 caption is hard to read. 13 px is for labels and metadata; running text stays at 16 px or more. Use only weights the font actually ships (or a variable axis), or the browser fakes bold.
4. **Leading moves against size**: body about 1.5, large headings about 1.1 to 1.2. Not one line-height for everything.
5. **Tracking**: tighten large headings slightly (about -0.02em above 24 px); open small uppercase labels (about +0.05em).
6. **Measure and wrapping**: cap paragraphs at about 45 to 75 characters (`max-width: 66ch`), whatever the container width. Balance short headings with `text-wrap: balance` and avoid a lone last word in paragraphs with `text-wrap: pretty`; never break lines by hand with `<br>` or `&nbsp;`, which break wrongly at every other width.
7. **Figures**: tabular numbers wherever digits align or update (DAT-1).
Define each step as one token bundling size, weight, line height and tracking; type keeps its own scale rather than borrowing spacing steps. Use one family (two at most).
**Detect.** More than about six font sizes; steps out of order (a "2xl" smaller than an "lg"); font sizes in px only; many weights; weights below 400 on small text; uniform line-height; full-width paragraphs; mixed families; one font size overridden at several breakpoints; `clamp()` with only `vw` in the middle; `<br>` inside headings.

### VIS-5 · Colour roles: dominant, secondary, one accent (P1)
**Applies to.** every screen: navigation, buttons, links, metrics, badges, status pills.
**Rule.** Distribute colour by role, roughly 60/30/10: a dominant neutral for backgrounds, a secondary step of the same family for surfaces (cards, nav, containers), and one accent spent only on primary actions, links, the active state and the one key number. Status colours (danger, success, warning) are semantic and used only for their meaning. When every nav item or metric gets its own colour, nothing stands out; mute everything else and the primary pops. The ground affects how a colour reads: an accent button on a surface of the same hue loses its edge however vivid both are, so give the primary action a surround that differs in lightness and check the accent on every surface it actually sits on. Quieted secondary actions (outline, ghost, neutral fill) still pass text contrast and never look like `disabled`; a control identified only by its fill keeps a 3:1 boundary against the surface (WCAG 1.4.11). Colour-to-emotion claims ("this hue signals trust") are folklore: take the hue from the brand, keep the role mapping.
**Detect.** Many unrelated hues on one screen; a different colour per nav item or metric; accent colour on decorative elements; coloured status pills everywhere; a primary button that blends into its card.

### VIS-6 · The danger colour is a budget (P1)
**Applies to.** uses of the danger or error colour.
**Rule.** The danger colour appears only on destructive actions and real errors. A red logout button or red decorative badges make the real delete look routine.
**Detect.** Danger tokens on non-destructive controls.

### VIS-7 · Contrast is a ratio (P0)
**Applies to.** every text and essential UI element (always check).
**Rule.** Contrast belongs to a text/background pair, never to a colour token alone: the same text colour can pass on one surface and vanish on the next. Body text at least 4.5:1 against its actual background; large text (24 px, or about 18.7 px bold) and essential UI parts (input borders, focus rings, icons that carry meaning) at least 3:1; aim for 7:1 (AAA) on critical text such as errors, prices and terms where the palette allows. Muted greys on nav links, card labels, subtitles, stat labels and placeholders are the usual failures, often only 1.5 to 2:1. Text dimmed by opacity is measured as rendered on its surface, gradient text at its weakest point. Check every pair in light and dark themes. Disabled controls are exempt, but their label stays legible.
**Detect.** Light grey text tokens; `opacity` below about 0.6 on text; text on images or gradients without a scrim; disabled-looking labels used for real content.
**Fix.** Change the lightness of the failing token, keeping its hue and the layout; a redesign is rarely needed.

### VIS-8 · Colour never carries meaning alone (P0)
**Applies to.** every status, state, series or group shown with colour: error and success messages, trends, chart series, chips, active nav items, selected icons (always check).
**Rule.** Every colour cue is paired with a second signal: an icon on error and success messages, an arrow plus a signed number on trends ("+14%"), patterns, textures or direct labels on chart series with shapes in the legend, a check or fill change on active chips, an underline or filled shape plus `aria-current` on the active nav item, a heading or position for colour-coded groups. Red against green is exactly the difference red-green colour-blind users (about 1 in 12 men) lose, so error and success, pass and fail, up and down never differ by hue alone. Before release, view key screens through a protanopia, deuteranopia and tritanopia simulator.
**Detect.** Status shown only by text or dot colour; red borders as the only error signal; charts distinguishable only by hue; groups distinguished only by tint.
**Fix.** For form errors add the icon, `aria-invalid="true"` and `aria-describedby` pointing at the message, so the meaning is not visual at all.

### VIS-9 · Dark mode is its own system (P1)
**Applies to.** products with a dark theme.
**Rule.** Not an inversion. Start from a near-black neutral (around 7% lightness), never pure black, with three or more surface tokens that get lighter as they rise (about +5 lightness points per step: base, surface, elevated). Elevation is shown by lightness because shadows barely show on dark; a darker, larger shadow may still support the top layers. Text is one light colour at a few opacities, never pure white: about 87 to 90% for headings and primary text, 60 to 70% for body and secondary, about 38% for disabled; every tier used for real content still meets VIS-7 on its surface. The accent keeps its hue but loses saturation (roughly 20%) and gains lightness so it does not vibrate or glow; then re-check the label on the accent fill and switch it to dark text, or darken the fill, if it drops below 4.5:1. Hairlines are white at a low alpha (about 6 to 12%) so they adapt to every surface; focus rings and input borders get their own dark values at 3:1. Photos are dimmed slightly (about `filter: brightness(.9)`, under the dark theme only); illustrations get redrawn dark variants (`<picture>` with a dark `media` source), because a filter leaves a light illustration glaring. The disabled tier is only for controls that really are disabled, never for information such as an upgrade hint. Alpha text over images or unknown backgrounds is replaced by solid computed colours. Text may need one weight step lighter. Implement as a semantic token swap (VIS-1) inside `@media (prefers-color-scheme: dark)`, plus a root attribute for a manual choice that is stored and applied before first paint so the page does not flash; declare `color-scheme` so native controls and scrollbars follow the theme.
**Detect.** `filter: invert()`; `#000` backgrounds or `#fff` text; one surface colour for page, cards and popovers; the same saturated accent in both themes; a light label on a softened accent with no contrast check; fixed grey borders; shadows as the only elevation in dark; a theme toggle that does not persist or flashes the other theme on load; no `color-scheme`, so form controls and scrollbars stay light.

### VIS-10 · Radius is a scale and a brand decision (P2)
**Applies to.** rounded elements (tooltips, badges, inputs, buttons, cards, modals, sheets, panels, avatars, focus rings), especially nested ones.
**Rule.** One scale (for example 4, 8, 12, 16, 24, plus a separate full/pill token) and radius grows with surface size: tooltips and badges 4, inputs and buttons 8, cards 12, modals 16, large panels and sheets 24; a small element is never rounder than the surface it sits on. Full radius only for one-line elements (pills, avatars, toggles). Nested corners stay concentric, so the band between the two curves is as wide across the corner as on the sides: **inner radius = outer radius − border − padding** (`r = R − b − p`: 24 outer and 8 padding give 16; with a 2 px border, 14), never below zero, and again at every nesting level. Giving the inner element the outer radius puts the two arcs on different centres, so an 8 px band swells to about 11 px in the corner (p × √2) and the inner element looks bloated. When padding differs per axis, use elliptical radii (`calc(R − px) / calc(R − py)`). The same subtraction holds for any control inside a control: a segmented-control thumb, a button inside an input, a chip inside a pill (`thumb = track − inset`: a 12 px track with a 4 px inset takes an 8 px thumb). Give the inner radius only to children that actually sit in a corner, not to `.card > *`; when the result is 1 to 3 px, square the inner corner or raise the outer radius, because a tiny radius reads as a rendering error. A ring outside an element is outer = inner + gap. Edges that touch the screen get no corner (a bottom sheet is rounded only on top). A flush image (no padding) takes the card radius, minus the border, on the corners that touch the card edge only (`border-radius: 24px 24px 0 0` for a top image); a smaller radius lets its corner poke outside the card's curve, and its corners against content stay square. Clipping with `overflow: hidden` on the card also works but clips popovers, shadows and focus rings too, so on cards that hold those, round the image itself. An inset image takes the card radius minus the inset. A pill is a large fixed value (`9999px`), never `50%`, which turns a wide box into an ellipse. `outline` follows the element's radius and grows with `outline-offset`, so it stays concentric; use it for focus rings (INT-1), and draw selection rings with a pseudo-element at radius plus gap. Choose the range once for the brand: the small end reads serious and corporate, the large end friendly, pills playful; rounded controls feel safer to touch.
**Detect.** The same radius on a card and the element nested inside it; off-scale radii (6, 10, 20, 30); small elements rounder than their containers; full radius on multi-line cards; a flush image rounded less than its card; one radius token on a segmented control's track and thumb; `.card > * { border-radius: … }`.
**Fix.** `border-radius: max(0px, calc(var(--radius-outer) - var(--border, 0px) - var(--pad)));` on nested surfaces that sit in a corner.

### VIS-11 · Elevation encodes hierarchy, lit from one source (P1)
**Applies to.** shadows, glows and elevated layers: menus, popovers, modals, dragged items, featured cards.
**Rule.** Elevation tells the user what sits above what, so spend it only where something floats or matters most, from a small token scale. Every elevation shadow comes from one light above the screen: x offset 0 and a positive y offset on every element, because mixed directions make the screen look assembled from unrelated parts (focus rings and inset shadows are outside this rule). Build each level from two layers, never one blur: a tight, darker contact layer that grounds the edge, the same on every level (`0 1px 2px` at about .12 alpha), and a soft layer whose y offset, blur and negative spread grow together with height while its alpha stays fixed (about .08): roughly 2/6 px for resting cards, 6/16 px for raised or hovered elements and menus, 16/40 px for modals and dialogs. The negative spread (about −2, −4, −8 px) tucks the soft layer under the element so it does not halo around the sides; lowering the alpha as the blur grows would make a modal's shadow fade out instead of lifting it. Use one shadow colour token, not raw black typed into each component. Page panels and rows get none; separate them with surface value steps and hairline borders. On dark surfaces elevation is carried mainly by lighter surfaces (VIS-9), and the shadow is a secondary cue. A shadow on every card means nothing floats: the strongest level goes to the one element that matters most (the recommended plan, the open modal), which also says so in text ("Recommended", `aria-modal`), since elevation is not announced. A soft glow tinted from the accent token (low alpha, about 15 to 35% on dark, far fainter on light) is an optional premium touch on that one element only. A shadow is decoration: a control whose boundary is only a shadow needs a border or fill at 3:1 (WCAG 1.4.11), and forced-colors mode removes `box-shadow` entirely. To animate elevation, fade a pseudo-element that holds the larger shadow instead of transitioning `box-shadow`.
**Detect.** The same heavy drop shadow on every panel; a single hard `box-shadow: 0 0 10px #000`; shadows with non-zero x offsets or different directions on one screen; soft layers with no negative spread haloing around raised elements; shadow alpha that drops as the level rises; shadows separating table rows or sidebars; input or button edges drawn only with a shadow; glows on several elements; a glow colour typed in rather than derived from the accent token; `transition: box-shadow` on hover.
**Example.**
```css
:root {
  --shadow-rgb: 0 0 0; /* or a dark tint of the surface hue */
  --shadow-1: 0 1px 2px rgb(var(--shadow-rgb) / .12), 0 2px 6px -2px rgb(var(--shadow-rgb) / .08);
  --shadow-2: 0 1px 2px rgb(var(--shadow-rgb) / .12), 0 6px 16px -4px rgb(var(--shadow-rgb) / .08);
  --shadow-3: 0 1px 2px rgb(var(--shadow-rgb) / .12), 0 16px 40px -8px rgb(var(--shadow-rgb) / .08);
  --shadow-glow: 0 0 60px color-mix(in srgb, var(--color-accent) 15%, transparent);
}
```

### VIS-12 · One focal point per view (P1)
**Applies to.** every screen; pricing tables, plan pickers, hero sections, nav bars and forms with a primary action.
**Rule.** Stack five levers on one entry point: size (the primary heading about twice body size; +20% reads as the same level), colour (one accent), contrast (bold against regular, filled against outlined, strong against muted text), space (about double the padding of its neighbours, one or two scale steps up) and weight. Primary action filled, secondary outline or text link, one filled primary per view: when a form's primary button is on screen, demote the nav CTA. When one option must stand out (a pricing tier, a CTA), start from a calm uniform baseline and change that one item on several channels at once (scale, accent fill, elevation, a truthful badge such as "Most popular", a specific label like "Get Pro" instead of the shared "Choose plan"), never colour alone. Quiet the alternatives with weight, fill and elevation, not by pushing their text below 4.5:1; users still compare them. Heading levels (`h1` to `h3`) follow the visual order.
**Detect.** Several equally loud buttons side by side; two accent-filled CTAs in one view; headings barely larger than body; everything bold; identical pricing cards with no featured variant; dimmed plan text that fails contrast.
**Fix.** Express emphasis as a component variant (`primary` / `secondary` / `ghost`; a `featured` card prop that changes elevation, border and badge) so only one primary exists per view. On mobile, stack the featured plan first with its badge rather than scaling it into overflow.

### VIS-13 · Layout sits on a grid, then breaks it on purpose (P2)
**Applies to.** page and section layouts, dashboards, app shells with sidebars.
**Rule.** A 12-column grid (or the project's grid) whose spans are ratios that state hierarchy: 4:8 for a narrow sidebar and wide content, 3:9 for a minimal sidebar and dominant content, 6:6 only for genuinely equal content; an unequal split (about 62/38) puts primary content on the larger side. At breakpoints reconfigure the grid instead of abandoning it (for example 12 columns at about 1280 px, 6 at 768, 4 at 480, 1 at 320) and re-declare spans for each. The gutter is a design choice on the spacing scale: about 8 px dense and technical, 24 px balanced, 40 px editorial, usually smaller on mobile. Align to shared edges. Break the grid deliberately (a full-bleed hero, a pull quote into the margin) only once the order exists. Visual reordering never changes reading or focus order, the single column works at 320 CSS px without horizontal scroll, and when columns narrow, decide where content wraps rather than dropping it.
**Detect.** Elements that almost align; ad-hoc widths; centred everything; `repeat(12, 1fr)` without `minmax(0, 1fr)` (long content blows out a column); `order` or grid placement that differs from DOM order; full-bleed via `width: 100vw` (adds horizontal scroll); horizontal scroll at 320 px.
**Fix.** `grid-template-columns: repeat(12, minmax(0, 1fr)); column-gap: var(--gutter);`, with named lines (`[full-start] … [content-start] … [content-end] … [full-end]`) and `grid-column: full` for bleeds.

### VIS-14 · Gestalt does free work (P2)
**Applies to.** layouts that group or order items: settings lists, navigation, toolbars, icon bars, card grids, dialogs over a page.
**Rule.** Proximity comes first (VIS-3). Similarity: things that belong together share one property, and changing that one property (not several) splits groups. Continuity: items on one axis read as a sequence, so align nav and lists instead of scattering them. Common region: a card or bordered section with a heading groups related controls more strongly than spacing, especially when they sit far apart (one card per settings group). Figure-ground: a dimmed scrim, optionally blurred, behind a dialog pushes it forward; dimming alone is enough on low-end devices. Closure: implied edges from spacing, alignment or partial outlines replace drawn boxes and dividers, but a barely visible implied border is never the only edge of a control (VIS-7). Back colour grouping with position, headings or shape (VIS-8).
**Detect.** Dialogs over an undimmed page; related settings scattered without a container; misaligned or scattered nav items; groups told apart only by colour; boxes and dividers around everything.

### VIS-15 · Icons are one set (P2)
**Applies to.** icons and icon buttons in toolbars, menus, nav bars and lists.
**Rule.** One family (one established library rather than several), one stroke weight across the set (2 px at 24 px is the common default; mixed weights look like four libraries), and one style rule: outline by default, filled only for the active or selected state, never a random mix. Draw on a 24 px grid (16 px for dense UI) with nodes on whole pixels, and render at the design size or integer steps (16, 20, 24, 32) so strokes stay crisp; if icons scale, keep the effective stroke equal across a row (`vector-effect: non-scaling-stroke` or the library's absolute-stroke option). Every icon sits in the same fixed box (the glyph varies, the container does not), which is also its hit area and is padded to the target sizes in INT-11. Round and pointed shapes are drawn larger than square ones to look the same size (VIS-16). Icons sit centred on the text line. A fill-for-active change also sets `aria-pressed` or `aria-current`; icon-only buttons get an accessible name, decorative icons `aria-hidden="true"`, meaningful icons 3:1 contrast.
**Detect.** Mixed icon libraries; mixed `stroke-width`; filled and outlined icons mixed without meaning; icons of different sizes in one toolbar; SVGs at fractional sizes or positions (an even icon centred in an odd box); icon buttons without `aria-label`; icons misaligned with adjacent text.

### VIS-16 · Optical corrections beat maths (P2)
**Applies to.** play buttons, icon and shape pairs, text in buttons and badges.
**Rule.** When the correct value looks wrong, adjust for the eye: shift a play triangle right (about 8% of its box, `translateX(8%)` or baked into the SVG), draw circles about 10 to 13% larger than squares beside them (equal area is 1.13; icon keylines use about 1.11; judge at the rendered size), keep nested corners concentric (VIS-10), centre labels on their cap height (CSS centres the line box including descender space, so labels without descenders look low; use `text-box: trim-both cap alphabetic` or a font-specific 1 px asymmetric padding, never a hard-coded nudge across fonts), and reduce weight one step on light-on-dark text through a theme token, keeping 4.5:1.

### VIS-17 · Gradients and glass are seasoning (P2)
**Applies to.** gradients (buttons, hero and card backgrounds, gradient text) and translucent "glass" surfaces.
**Rule.** Gradients stay between neighbouring hues (at most about 60° of hue travel; complementary ends turn muddy in the middle), derive their stops from the accent token, move lightness in one direction, and interpolate in a perceptual space (`in oklch`) to avoid a grey dead zone. Linear ramps on surfaces and buttons read best on a diagonal that matches the product's implied light source (top-left to bottom-right, `135deg`, is the usual pick); plain vertical or horizontal ramps look like default fills. Large surfaces get a few soft radial glows (2 to 4 points) as ambiance behind content rather than a wash over it. Gradient text only on one large headline, checked for contrast at its weakest point, with a solid `color` fallback and a forced-colours fallback; body text stays solid and never sits on the transition zone. Add subtle grain (about 2 to 3% noise) if banding shows. Glass is four layers together (a translucent tint from the theme's surface role, `backdrop-filter: blur(about 20px)`, a 1 px light hairline, a large faint shadow such as `0 8px 32px` at about 15% black) and only works over a varied backdrop; over a flat background it is a grey card. Text on glass stays fully opaque and passes 4.5:1 against the lightest and darkest regions that can appear behind it, not the average; over user images add a stronger tint or a scrim. Give an opaque fallback in `@supports not (backdrop-filter: blur(1px))`, switch to it under `prefers-reduced-transparency: reduce`, raise tint and border under `prefers-contrast: more`, and never animate the blur radius or put glass on long scrolling lists.
**Detect.** Gradient text in body copy; `background-clip: text` with no solid fallback; gradients across opposite or many hues; sRGB ramps between distant hues; glass panels over flat colour; translucent panels that fail contrast; `backdrop-filter` without an `@supports` or reduced-transparency fallback.

### VIS-18 · Layering without z-index wars (P1)
**Applies to.** overlapping layers: dropdowns, menus, popovers, tooltips, modals, toasts, sticky headers.
**Rule.** `z-index` only orders positioned elements (relative, absolute, fixed, sticky) and flex or grid items, and only against siblings in the same stacking context: a child at 9999 inside a parent context at 1 still sits below a sibling context at 2. Contexts come not only from position plus z-index but also from `opacity` below 1, `transform`, `filter`, `backdrop-filter`, `will-change`, `contain` and fixed or sticky position, so an animated ancestor is the usual reason a high number "does nothing". Give reusable components their own context with `isolation: isolate` (no position or layout change) and keep a small named scale (base, dropdown, sticky, overlay, modal, toast). Render menus, popovers and dialogs outside clipping and stacking ancestors, through a portal or the top layer (`<dialog>` with `showModal()`, the `popover` attribute); `isolation` does not escape `overflow: hidden`. Debug by finding the ancestor that creates the context (computed styles, a 3D z-index view), not by escalating numbers.
**Detect.** Escalating values (999, 9999, 99999); `z-index` on a static element that is not a flex or grid item; component-internal z-indexes without `isolation: isolate`; overlays rendered inside a transformed or `overflow: hidden` ancestor.

### VIS-19 · Depth tricks stay subtle (P2)
**Applies to.** 3D tilt and `translateZ` effects, hover lift on cards and tiles, parallax layers.
**Rule.** Transform-based depth supports shadows and surface steps (VIS-11, VIS-9); it never replaces them. `translateZ` and `rotateX` only read inside a perspective (about 800 to 1200 px on the container, or `perspective()` in the transform); without one only the scale does anything. Keep it small: tilt about 2°, on hover or press rather than at rest (a tilted card can blur its text); card hover lift and timing follow MOT-9 (about 8 px, no scale of the card itself), reinforced with a stronger shadow or border. Parallax speeds are relative: the foreground moves with the scroll and background layers at a fraction of it, never faster. Scope hover depth to `@media (hover: hover)`, give `:focus-visible` the same emphasis, and remove tilt and parallax under reduced motion (MOT-13); hover timing is MOT-9, scroll binding MOT-12.
**Detect.** `translateZ` with no `perspective` on an ancestor; permanent `rotateX`/`rotateY` on text-bearing cards; hover scale above about 1.05; layers moved faster than the scroll; parallax with no reduced-motion handling.

### VIS-20 · Cards: one entity, padding, hierarchy, an edge (P2)
**Applies to.** cards and tiles: content, product and dashboard cards, and settings or form sections drawn as cards.
**Rule.** A card is one entity with a title, a subject and a destination; settings groups and form sections are labelled sections with dividers, not cards. Never nest cards: inside a card or panel, group with section labels and dividers, so padding does not stack (24 + 24 + 24). Pick the edge from the background, one treatment each: a border on a plain page, a shadow on a tinted one, flat inside a panel; border plus shadow together is noise. In a grid all card media share one aspect ratio (`aspect-ratio: 16 / 9; object-fit: cover`, with `object-position` on the focal point), cropped, never stretched, and the parts line up across the row: make each card a subgrid of the parent's rows (`grid-template-rows: subgrid; grid-row: span 3` for media, body and footer, one row per part) so titles and footers align whatever the text length. A card that appears in both narrow and wide slots switches layout with a container query on its wrapper (`container-type: inline-size`, `@container (min-width: 400px)`), not a viewport breakpoint. Then a card looks finished when four things are decided. Padding: generous and even (about 24 px on all sides, 16 px between image, tag, title, body and meta), never content pressed to the edge. Hierarchy: the title clearly leads (weight 600 and larger, about 18 px against 14 px), the description is regular weight in the muted text token, which still passes 4.5:1 on the card (VIS-7). Edge: the one treatment picked above; when it is a shadow, VIS-11's resting level; on dark surfaces a 1 px hairline at about 10 to 12% of the text colour, since shadows barely show there; radius from the scale (VIS-10). Hover: only if the whole card is clickable, a lift with a stronger shadow (or a stronger border when the edge is a border), mirrored on `:focus-visible` (MOT-9). A clickable card is one target: put the link on the title and stretch it over the card (`a::after { content: ""; position: absolute; inset: 0 }`) so the accessible name stays short and text stays selectable. Secondary actions move to an overflow menu raised above the stretched link (`position: relative; z-index: 1`) with its own name; a card with two buttons is a panel.
**Detect.** Card padding under about 16 px; title and description in the same size and weight; flat cards on a dark page with neither hairline nor surface step; hover lift on a card that does nothing; several nested interactive elements inside a clickable card; a whole card wrapped in `<a>` around buttons; cards inside cards; settings sections boxed as cards; mixed image ratios in one grid; footers at different heights across one row of cards; border and shadow stacked on a tinted page.

### VIS-21 · Layout uses the platform, not scripts and hacks (P2)
**Applies to.** page shells and full-height sections, sticky headers, centred content, components that sit in slots of different widths, scroll-snap rows, stylesheet overrides.
**Rule.** When a script or a hack only reproduces what CSS can state directly, use the CSS primitive, check current browser support, and keep a fallback (`@supports`, or a line the new value overrides):
- **Full-height shells**: `min-height: 100dvh` after a `min-height: 100vh` fallback. `height: 100%` resolves to nothing unless every ancestor has a height, and a fixed `100vh` hides content under mobile browser toolbars. A child that fills its parent uses flex or grid stretching (`flex: 1`, `1fr`), not viewport units.
- **Sticky headers**: `position: sticky; top: 0` instead of a scroll listener that toggles a class, plus `scroll-padding-top` equal to the header height so anchor targets and focused elements are not hidden underneath (WCAG 2.4.11). Sticky does nothing inside an ancestor with `overflow: hidden`, `auto` or `scroll` (`clip` is fine); cap a sticky header's height on small screens.
- **Centring**: grid or flex alignment (`display: grid; place-items: center`). Absolute positioning with `translate(-50%, -50%)` is only for overlays that must leave the flow, such as a spinner over a card.
- **Component-responsive layout**: a component that lives in a sidebar and in a main column responds to its container (`container-type: inline-size` on the wrapper, `@container` rules inside), not to the viewport or `window.innerWidth`.
- **Cascade**: declare the layer order once (`@layer reset, base, components, utilities;`) instead of winning with `!important` or longer selectors; nest selectors shallowly, mainly for states and local media queries.
- **Scroll snap**: `scroll-snap-type: x proximity` when an item can be larger than the viewport, since `mandatory` can make part of it unreachable; snapping is behaviour only, so a snap carousel still needs visible previous and next controls and keyboard access.
Spacing between siblings is VIS-2, stacking VIS-18, truncation DAT-9, styles that read DOM state INT-22, scroll restoration DAT-8.
**Detect.** `scroll` listeners that add a "stuck" or "scrolled" class; `height: 100vh` on page shells; chains of `height: 100%`; `top: 50%; left: 50%; transform: translate(-50%, -50%)` on in-flow content; reusable components switched by `window.innerWidth` or viewport media queries; `!important` in component styles; `scroll-snap-type: … mandatory` on items taller or wider than the viewport.
