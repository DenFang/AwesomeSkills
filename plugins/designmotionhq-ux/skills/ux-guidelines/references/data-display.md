# Data display

Tables, lists, numbers, search, filters and charts. Data UI looks cheap when it is a grid of divs with default text; it looks engineered when alignment, density and state are decisions.

Severity: **P0** misleads or hides data, **P1** friction, **P2** polish.

---

### DAT-1 · Numbers are a system (P1)
**Applies to.** numbers shown in columns, counters, prices, stats, timestamps.
**Rule.** Any column, counter, price or live value uses tabular figures (`font-variant-numeric: tabular-nums`) so digits share one width and nothing wobbles. Numbers right-aligned, with their column header aligned the same way; text left-aligned. Large values abbreviate in tiles (1.2K, 3.4M) with the exact value on hover or in a tooltip. Times under a day are relative ("2h ago"), older are absolute ("Mar 3"). In columns, the currency symbol is pinned, decimals are consistent and the amounts align on the decimal. Format with `Intl.NumberFormat` (`notation: "compact"` for 3.4M), `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat` for the user's locale, since separators, symbol position and abbreviations differ; check that the font has tabular figures (`tnum`, else `font-feature-settings: "tnum" 1`), keep one number of decimals per column, and pin the currency symbol in its own slot or put it in the header so it does not ragged the column. The exact value behind an abbreviation or a relative time is reachable on focus and tap, not only hover (`<abbr title>`, `<time datetime>`, or an accessible name with the full value), and relative labels re-render as time passes. On phones, big figures stay on one line (`white-space: nowrap`, a capped size such as `clamp(1.25rem, 6vw, 1.875rem)`), so a sign or unit never wraps alone.
**Detect.** Numeric columns left- or centre-aligned; proportional digits in tables or counters; hand-rolled formatting with string concatenation; mixed decimal places in one column; raw clock times on recent activity or "41 days ago" on old items; abbreviations whose exact value is hover-only.

### DAT-2 · Table: six decisions (P1)
**Applies to.** tables and data grids.
**Rule.**
1. **Align**: numbers right with tabular figures, headers aligned like their column, text left, nothing centred except icons.
2. **Rows**: one hairline and a hover tint. Compact rows never get stripes; subtle zebra stripes are acceptable only at comfortable or spacious density or on very wide tables (about 12+ columns).
3. **Density**: row height is a token with three values (about 40 compact, 48 default, 56 comfortable), set on the table root and switched by one control; let the user or role pick and persist the choice. Compact rows are below a touch target, so offer them on fine pointers or keep the hit area taller than the row.
4. **Sticky**: header pinned on vertical scroll, identity column pinned on horizontal scroll, each with a soft shadow that appears only while content is under it.
5. **Cells**: a missing value shows a dash with an accessible "No value", never a blank; zero is a real `0` and loading is a skeleton, not a dash. Long text truncates to one line with the full value on hover and focus; numbers never truncate (widen the column or abbreviate with a unit); one line per row.
6. **Actions**: no column of repeated pencils and bins; reveal row actions on hover and `:focus-within` (kept in the tab order, never `display: none`), and under `(hover: none)` show a menu button per row named for the row ("Actions for INV-2043"). Show the sort arrow only on the active column (a faint one on header hover and focus).
Sticky cells need an opaque background, the corner header sits above both pinned edges, and sticky fails if an ancestor between the cell and the scroller has `overflow: hidden`.
Use semantic `<table>` markup (or a full ARIA grid when cells are interactive), not divs. Sorting is DAT-3, selection DAT-4.
**Detect.** `<div>` grids pretending to be tables; centred numbers; blank cells; per-row icon clutter; header scrolling away; row heights hard-coded per screen instead of a density token; stripes on compact rows.

### DAT-3 · Sorting is tri-state and visible (P1)
**Applies to.** sortable tables and lists.
**Rule.** Clicking a header cycles ascending, descending, then back to the original order with no arrow, because the natural order (insertion, date) often carries meaning. The header label is a `<button>` inside the `<th>`; show the sort arrow only on the active column, and put `aria-sort="ascending"`/`"descending"` on that column alone. Rows that animate to their new positions reorder instantly under reduced motion.
**Detect.** Two-state toggles that lose the natural order; arrows on every column; click handlers on bare `<th>` elements.

### DAT-4 · Selection is application state (P1)
**Applies to.** lists or tables with multi-select, header select-all checkboxes, selection bars.
**Rule.** The header checkbox has three states (empty, an indeterminate dash for any partial selection, checked) and clicking the dash selects all, never clears; set `input.indeterminate` (or `aria-checked="mixed"`). The whole row is the selection target, not only the tiny checkbox, and a selected row shows redundant cues (tint, a leading accent bar and the tick, never tint alone) while the real checkbox, labelled with the row's name, remains the accessible control; if a row click also opens details, give details their own link. Shift-click selects the inclusive range from the last clicked row in the current sort order (Shift+Space or Shift+Arrow in grids). Selected IDs live in app state and survive paging, filtering and virtualisation. A selection bar shows "N of M selected" with Clear selection, announced politely. When select-all covers only the visible page, say so and offer "Select all 247 matching" with the true count (store it as a query-scoped flag plus excluded IDs, not every ID). When filters change, keep the IDs that still match and update the count live; never act on rows that no longer match without saying so.
**Detect.** Two-state header checkboxes; selection stored in DOM checkboxes; selection lost on page change; "Select all" that silently means "this page"; checkbox-only row selection.

### DAT-5 · Bulk actions run and offer undo (P1)
**Applies to.** bulk actions on selections and their selection bars.
**Rule.** Bulk actions echo the count in the button ("Delete 247", "Archive 12 projects") and in the result ("247 members deleted"), run immediately and offer an undo of about 10 s with a draining countdown instead of a confirm dialog, which gets clicked through and still offers no way back. That only works when the action is really reversible (soft delete, or a commit deferred until the window closes); the undo pauses while hovered or focused, stays keyboard reachable, is also offered in a "Recently deleted" view (STA-14), and is styled neutral or accent, not danger. After the action, the emptied or reduced view says what happened ("247 removed a moment ago"). Irreversible bulk actions (permanent purge, external side effects) still need explicit confirmation that states the count (INT-9).
**Detect.** "Are you sure?" modals before reversible bulk actions; bulk buttons without the count; undo toasts that auto-dismiss while focused.

### DAT-6 · Tables on narrow screens become rows, not tiny tables (P1)
**Applies to.** tables shown on narrow screens or in narrow containers.
**Rule.** Do not shrink a wide table or scroll it sideways on a phone, and never hide decision columns (status, deadline) behind a horizontal swipe. Rank columns by the user's task, not source order: identity and value first, state second; internal IDs and secondary metadata go first. Each row becomes a two-line card (name left, amount right, state and secondary info below) that is a comfortable touch target; amounts stay in one fixed top-right slot with tabular figures so the cards still read as a column; only ambiguous values get inline labels ("Due Mar 04"; a currency amount needs none). When headers disappear, sorting moves into an explicit control ("Sort: Due date"). Hidden fields are one tap away, expanded in place (a button with `aria-expanded`) or in a bottom sheet for the full record, never a new page. Let the table switch on its own width: give its wrapper `container-type: inline-size` and pick the threshold from the width at which all columns are readable (often about 640 to 700 px), so the same component also becomes cards in a narrow desktop side panel. Restyling a `<table>` with `display: block` can drop its semantics in some browsers: keep explicit `role="table"`/`row`/`cell`, or render the card view as a list with labelled fields.
**Detect.** `overflow-x: auto` tables with six or more columns on mobile; font-size reduced to fit; columns dropped by position; amounts that float with name length in cards; breakpoints at device widths (375/768/1024) instead of the table's own width.

### DAT-7 · Pagination is stable and restorable (P1)
**Applies to.** paginated or infinitely loaded lists, pagers, "Load more" buttons.
**Rule.** Choose by job: numbered pages for tables people jump around in (with a "Go to page" input for large counts), "Load more" for user-paced lists, infinite scroll only for feeds, and then keep the footer reachable. Offset pagination drifts on live data: one insert shifts every page and shows an item twice, a delete skips one. Use cursor (keyset) pagination, ordered by a unique indexed key with opaque cursor tokens, for live lists, feeds and "Load more"; keep offset with jump-to-page only where data is mostly stable, or pin it to a snapshot ("created before" the first load). Truncate the pager to about seven cells: first, gap, current with its neighbours, gap, last, plus previous/next; on phones drop the neighbours or show "Page 500 of 833". Keep the page or cursor in the URL (`?page=500`, `?after=…`) so refresh, back and shared links keep the view. Mark it up as `<nav aria-label="Pagination">` with real links, `aria-current="page"`, named previous/next and non-interactive ellipses. After a page change move focus to the top of the results or announce "Page N of M"; after "Load more" announce how many items arrived and focus the first new one.
**Detect.** Offset pagination on live data; pagers with every page number; page held only in component state; pager buttons without `aria-current`; page changes that leave focus on the pager in silence.

### DAT-8 · Scroll position is navigation state (P1)
**Applies to.** lists and feeds that open detail pages, single-page-app routing, anchor and jump links, sticky headers, infinite feeds with footers.
**Rule.** Going back returns the user to where they were. Save the scroll position, together with the loaded count or cursor, per history entry (the router's location key, not the pathname, so two visits to the same list restore independently) when leaving, and restore it after the list has rendered its data and media heights; for virtualised lists store the first visible item and its offset rather than pixels. Set `history.scrollRestoration = 'manual'` only when the app restores scroll itself, or use the router's own (`<ScrollRestoration />`, Vue Router `scrollBehavior`). Return keyboard focus to the item the user opened and highlight that row briefly. Clear sticky headers once in CSS: `html { scroll-padding-top: var(--header-h) }` (or `scroll-margin-top` on targets) covers restores, anchor jumps, `scrollIntoView` and focus scrolling, instead of subtracting a literal height in script. An infinite feed must not be the only route to footer links (contact, legal, policies): add a "Load more" button, stop auto-loading after a few pages, or put those links elsewhere (CON-9, DAT-7).
**Detect.** `window.scrollTo(0, 0)` on every route change; back navigation landing at the top of a long list; restore before data loads; anchor targets hidden under a sticky header (no `scroll-padding-top`/`scroll-margin-top`); a footer that infinite loading keeps pushing away.

### DAT-9 · Layouts survive real content (P1)
**Applies to.** text slots in flex and grid rows: names, titles, filenames, emails, paths, URLs, user-generated messages and comments, live numbers.
**Rule.** Design and test every text slot with real lengths, not short placeholder names. A flex item cannot shrink below its longest unbreakable text (`min-width: auto`), so `text-overflow: ellipsis` does nothing until the shrinking child gets `min-width: 0` (in grid, a `minmax(0, 1fr)` track), and an ancestor that refuses to shrink needs the same fix. Truncate in the middle where the end carries meaning (file extension and version, email domain): a shrinking head span with the ellipsis plus a non-shrinking tail span, keeping the full value in `title` and in the accessible name. Numbers that update live or sit in columns use tabular figures (DAT-1). Containers of user text use `overflow-wrap: anywhere` so URLs, tokens and IDs wrap inside the bubble; `word-break: break-all` chops ordinary words and is wrong for prose, and long natural-language words prefer `hyphens: auto` with a `lang`. Minimum fixtures for every slot: empty, one character, and about 40 characters plus an emoji; add right-to-left and CJK text and a 320 px viewport where the product supports them.
**Detect.** `text-overflow: ellipsis` inside a flex row with no `min-width: 0` on that item or `overflow: hidden` on it; end-truncated filenames or emails; proportional digits on live counters; message bubbles without `overflow-wrap`; `word-break: break-all` on body text; fixtures and stories that use only short names.

### DAT-10 · Filters show their logic and their effect (P1)
**Applies to.** filter chips, faceted filters and active-filter bars.
**Rule.** Chips have three distinct states: idle (surface and border), active (accent fill plus a check, never colour alone; text 4.5:1 on the fill, chip edge 3:1 against the page), and disabled when they would return nothing (prefer `aria-disabled` with the zero count shown, so the option stays discoverable). A toggle chip is `<button aria-pressed>`; an exclusive group is a radio group. Options combine with OR inside a group and AND across groups; make it visible whether a tap widened or narrowed the set. The result count updates on the same frame as the tap, because a silent tap gets tapped again and toggles off; with server results, flip the chip at once and show a pending count rather than freezing the old number, and announce the count politely with a debounce. One "Clear all" beside the active-filter count resets everything, is hidden or inactive at zero, and leaves focus on the count or first chip. On phones, chips sit in one horizontally scrolling row with an edge fade and end padding so the last chip can clear the fade; a wrapped wall of chips buries the results. Active filters stay pinned in a sticky bar of removable chips with the count, so users see why the list shrank.
**Detect.** Active and idle chips that look alike or differ only by colour; result counts that update late or never; no clear-all; `flex-wrap: wrap` on mobile chip rows; chips built from `<div>` without `aria-pressed`.

### DAT-11 · Search is five parts (P1)
**Applies to.** search inputs, autocomplete suggestion lists and search results.
**Rule.** A real label (visible or `aria-label`) plus a placeholder that says what can be searched ("Search by name, SKU or brand"); the placeholder is a hint, never the only label. On focus with an empty field, show recent searches (about five, one tap fills and runs, each removable plus clear-all, never in shared contexts without consent). Autocomplete keeps prefix matches, ranks by real usage (with a fallback before usage data exists), highlights the matched part, tags each row with a category or scope, and stays short enough to scan without scrolling (about 3 to 8 rows). Use the combobox pattern: `role="combobox"` with `aria-expanded` and `aria-controls` pointing at a listbox, `aria-activedescendant` for the highlighted option, Up/Down move, Enter selects, Escape closes, visible focus on the input and a non-colour cue on the active option, and the suggestion count in a polite live region. Debounce requests by about 150 to 300 ms, cancel stale ones and keep previous results visible while fetching. Zero results keep the query visible and editable and offer a way on: "Did you mean", popular searches, a category to browse, recently viewed items.
**Detect.** "Search…" as the only placeholder or label; empty dropdown on focus; suggestions sorted alphabetically; zero-results dead ends; requests per keystroke.

### DAT-12 · Command palette is a system (P2)
**Applies to.** command palettes and quick switchers.
**Rule.** Open with Cmd+K (Ctrl+K off macOS) and a visible button. Never empty on open: recent commands with the first one highlighted, so Enter works before typing. Match fuzzy subsequences ("stg" finds Settings), rank prefix and word-start matches above scattered ones and then by recency, and highlight the matched characters (`<mark>`, keeping the plain label as the accessible name). Group results under labelled sections (Recent, then Actions, then Pages), using `role="group"` labelled by a header that is not selectable. Keyboard-first: arrows move with the highlight scrolled into view, Enter runs, Escape closes; rows with a global shortcut show it right-aligned. Async commands keep the palette open with a spinner on that row only and load results in place with a count (`aria-busy` on the list, a polite announcement, errors inline), never a full-screen block. Rows that open a sub-level carry a chevron; the current level shows as a chip in the input, and Escape (or Backspace in an empty input) goes back exactly one level with the parent row still highlighted. To feel instant, render the last cached results for the query on open and replace them row by row as fresh ones arrive, without reordering rows under the cursor (keep the selection by item ID); show background work as a thin progress line under the input after about 100 to 200 ms, never a spinner over an emptied list. A footer always names the primary action for the selected row with its key ("Open Application ↵") in the same place for every row, plus "Actions ⌘K" for a per-row action panel that lists every action with its shortcut, so the shortcuts are learnt by exposure (CON-10); destructive actions there keep undo or confirmation. A lightweight, non-modal launcher may blur what sits behind it (about 20 px, with a tinted surface so text keeps 4.5:1 and an opaque fallback under reduced transparency) instead of a dark veil; a true modal still dims. Build it as a modal dialog holding a combobox and listbox with `aria-activedescendant`. It accelerates visible navigation; it never replaces it.
**Detect.** Exact substring filtering (`label.includes(query)`); one flat result list; a blank palette on open; a global spinner while one command loads; Escape closing the palette from a sub-level.

### DAT-13 · Charts tell the truth (P0)
**Applies to.** charts and graphs.
**Rule.** The visual change must equal the data change. Bar, column and area axes start at zero, no exceptions; a line chart may start elsewhere when the variation is the message, with visible tick labels. The question picks the form: bars compare, lines show change over time, pies only with about five slices or fewer (sorted, from 12 o'clock), otherwise a sorted bar chart. Proportion line charts so the average slope sits near 45°, neither squashed flat nor stretched into a spike. Remove non-data ink (heavy gridlines, 3D, shadows, boxed legends) and label series at the line end, keeping a legend or small multiples when labels would collide. Spend colour on meaning: one accent on the value that carries the message against neutral others; categorical scales for groups, sequential for magnitude, diverging around a meaningful midpoint, varying lightness and not only hue; data marks keep 3:1 against their neighbours. Title the chart with the takeaway ("Revenue flat since March"). Past about five series, a line chart stops answering anything: switch to small multiples or a sortable table with a sparkline and the change as text. Annotate spikes, dips and breaks on the chart itself with their cause as real text ("Launch day"), not in a comment thread. A line chart that does not start at zero labels its axis range, and the focus series differs by stroke weight and a direct label as well as colour. Any delta printed on a chart is computed from the data (925 to 1,000 is +8%, not +13%). Never encode a series by colour alone, and give the chart a text alternative stating the takeaway (`<figure>` with `<figcaption>`, or `role="img"` with a label) plus the values as a table. Animated axis changes respect reduced motion.
**Detect.** Truncated bar baselines (`beginAtZero: false`, a domain minimum above 0); pies with many slices; a different hue on every bar; rainbow series; 3D charts; generic metric titles.

### DAT-14 · Dashboards lead with the number that matters (P1)
**Applies to.** dashboards, KPI rows and metric tiles.
**Rule.** A KPI row is read once, so it must show at a glance which value needs attention. One primary metric, larger, with its breakdown; secondary metrics smaller; at most 4 cards in a row (a fifth gets skipped), the rest in a second row, a tab or the detail view. One headline number per card, with the unit on the value (`$48.2k` under "Revenue", not "Revenue ($k)" above 48.2). Each number has a shape: a delta that names its comparison period ("+8% vs last 7 days", "+12.5% vs Jul"), or a sparkline. Colour follows the metric's direction, not the delta's sign: rising churn, refunds or costs are bad news. Normal deltas stay neutral and only the values that are actually off get the danger role, so the problem stands out; that value also carries a non-colour cue such as an arrow with "Up" or "At risk" (VIS-8). Where a target exists, show it on the card: value over target ("48.2 / 60k"), a bar to the target, the deadline and a status sentence ("On track: 80% of the goal, 7 weeks left") computed from the share of the goal reached against the share of the period elapsed, with the bar coloured by that status. A goal bar is a `<meter>` (min, max, value, an accessible name and `aria-valuetext`), not `role="progressbar"`, which is for task progress. A count-up lands on the exact final value at the static precision, shows the final value at once under reduced motion, and never sits in a live region. Title the page by what it shows ("Revenue · Aug 1–31"), not a greeting. No icon tiles competing with the numbers. See CON-6 for the other generated-dashboard tells.
**Detect.** Deltas with no period; every delta coloured by its sign; a rising cost or churn shown in the success colour; five or more cards in one row; units only in the label; a target that exists but is not on the card; `role="progressbar"` on a goal; a count-up that ends on a rounded value.

### DAT-15 · Avatars are a system (P2)
**Applies to.** avatars and user identity chips.
**Rule.** Fallback chain: image, then initials from the name, then a generic icon; never the browser's broken-image glyph. Render the initials underneath and fade the image in on `load`, keeping the initials on `error`, at a fixed size so nothing shifts. Background colour derives from a stable hash (FNV-1a, djb2) of the user ID, not the display name, modulo a fixed set of the project's tokens that give the initials 4.5:1, so the same person looks the same on every screen and survives a rename. Two initials by default (first and last, locale-aware, handling single-word names and non-Latin scripts), one only below about 20 px. Groups overlap by about a third of the diameter with a ring in the surface colour, cap at about four faces and end with a "+N" chip named "3 more members" that lists everyone on hover, focus or tap. Presence is one ring around the avatar (online, away, offline mapped to the success, warning and neutral roles), never an extra pill or dot, and also differs by ring style or text (`aria-label="Sarah Chen, online"`). Three size tokens only (about 24 list, 32 header, 40 profile); pad the hit area when an avatar is interactive. An avatar next to the printed name is decorative (`alt=""`); alone, its `alt` is the name.
**Detect.** `<img>` avatars with no `onError` fallback; colours from `Math.random()` or from the name; single-letter initials at normal sizes; uncapped avatar rows; a status pill stacked on an avatar; avatar sizes outside three tokens.

### DAT-16 · Chat threads keep the reader in place (P1)
**Applies to.** chat, messaging and comment threads.
**Rule.** Group consecutive messages from one sender within about 2 min on the same day under one avatar and name, about 4 px between lines inside a group and 16 px between groups; a date divider or system message breaks the group. Date dividers instead of timestamps on every row; the exact time appears on hover, focus and long press, and is in a `<time datetime>` element. The sent message appears on the frame of Enter with a pending state and confirms quietly ("Sent" a beat later), never a spinner in its place; keep a client ID to reconcile the server echo and reuse it on retry. A failed one stays in place with "Not sent · Retry", danger role plus icon and text. Track whether the reader is at the bottom (within about 40 to 80 px): there, follow new messages; scrolled up, append without changing `scrollTop` (0 px shift) and show a "3 new messages" pill named "3 new messages, jump to latest". The message list is a `role="log"` live region, throttled in busy channels. Typing indicators are the last item in the flow with the typer's avatar, not a bar above the composer, and nothing moves when they leave (STA-18). The composer grows to about five lines then scrolls, attachments preview as chips above the text, Enter sends and Shift+Enter adds a line, but Enter never sends during IME composition (`event.isComposing`), and on soft keyboards the send button is primary (FRM-20).

### DAT-17 · Ratings are honest (P2)
**Applies to.** star rating inputs, average rating displays and review summaries.
**Rule.** Keep two values: a preview that follows hover, focus or a touch drag, and the committed value. Render the preview when there is one, change the committed value only on click or release, and clear the preview on pointer leave, blur and `pointercancel`, so the display always snaps back to what was saved. Preview half stars only if halves are stored. On commit, fill the stars left to right about 30 ms apart (instantly under reduced motion). Averages render as fractional fills, clipping the last star to the exact fraction (4.4 is four stars and 44% of the fifth, never five), with the number printed beside it; compute summaries from the data and round to one decimal correctly, never in the flattering direction. Summarise with the number (or a ring), the review count and a distribution per star; keep the star row for input. The input is a radio group labelled per value ("4 stars") that arrow keys change; the read-only average has a text alternative ("Rated 4.4 out of 5 from 1,204 reviews") with decorative icons hidden; filled and empty stars differ by more than colour; each star is at least 24 px, ideally 44 px on touch.
**Detect.** `Math.round` or `Math.ceil` on averages before drawing stars; hover writing straight into the saved value; no reset on `pointerleave`/`blur`; star icons with no text value.

### DAT-18 · Calendar week views (P2)
**Applies to.** calendar day and week views.
**Rule.** A strict time grid: seven day columns, one row per hour (days with a daylight-saving change have 23 or 25), hour labels on the grid lines rather than centred in cells, and a now line that updates at least every minute. Open scrolled to the current time on first render only, not midnight and not after the user has scrolled. Events use a thin stripe (about 3 px) in the calendar colour on a faint tint (about 10%) of it, with the title in the normal text colour at 4.5:1, instead of saturated fills with white text; the calendar name stays available as text, since the stripe colour alone cannot carry it. Two or three concurrent events split the column at equal widths instead of hiding behind "+1 more" (cluster collisions by rendered height, not raw duration); beyond that, cap the columns with an explicit overflow (month views may use "+N more"). Height equals duration on a fixed scale (for example 60 px per hour) with a one-line minimum, and a thin bar below that whose title is reachable on hover, focus and tap. Drag on empty space draws an event snapped to 15 minutes with a live start, end and duration readout; the body moves the event keeping its duration; resize only from the bottom edge. Every drag has a click or keyboard path (click a slot to create, edit times in a form, arrows move in 15-minute steps), and each event is focusable with a name holding title, day and time range. All-day events live in a pinned row under the day headers, never as full-height blocks. Labels use the user's locale and time zone.

### DAT-19 · Admin screens follow the task, not the schema (P1)
**Applies to.** admin and back-office data screens: user, order and record tables with row actions.
**Rule.** Before building, name who uses the screen every day and the worst mistake they could make, and let both shape it. Show the columns the task needs (often about five, not the twelve the schema has): merge avatar, name and email into one identity cell, show status as a badge with icon and text, time as relative "last seen", and drop internal IDs and created/updated stamps unless the job needs them. When the job is finding a record, search is the primary control beside the title, with one primary button. Destructive row actions leave the row: they sit last in a row menu (`aria-label="Actions for Sarah Chen"`), in the danger role with an ellipsis label ("Delete account…"), and open a dialog that names the object; irreversible ones need typed confirmation (INT-9), recoverable ones get undo (STA-14). Spec every state the screen can reach before coding (STA-1): a skeleton matching the table one to one, an empty state with one action ("Invite your first user"), a load error as an inline banner with Retry above any rows already shown, success where the user looks, and partial or offline where they can happen.
**Detect.** A table whose columns mirror the database model (`id`, `created_at`, `updated_at`); a one-click Delete beside Edit on every row; no empty or loading state; search hidden in a toolbar on a lookup screen.
