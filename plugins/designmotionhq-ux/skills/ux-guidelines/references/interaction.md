# Interaction, navigation and overlays

How controls respond, how people move around, which overlay to use, and how keyboard, mouse and touch all reach the same actions.

Severity: **P0** unreachable, inaccessible or destructive by accident, **P1** friction, **P2** polish.

---

### INT-1 · Focus is always visible (P0)
**Applies to.** every focusable element, the page's tab order and skip links (always check).
**Rule.** Never remove the focus outline without a better replacement: about 2 px, offset about 2 px, at least 3:1 contrast against the element and every surface it can sit on (check light and dark themes), shown via `:focus-visible` so keyboard users get it and mouse clicks do not (text inputs still show focus on click; leave that alone). Draw it with `outline`, not only `box-shadow`, which forced-colours mode removes; on mixed backgrounds a two-tone ring (a surface-coloured gap plus a contrasting ring) keeps 3:1 everywhere. Sticky headers and overlays must not cover the focused element. The focus style differs from the selected/active style. DOM order matches visual order: reorder the markup, not the layout. On content-heavy pages a "Skip to main content" link is the first focusable element, visually hidden until focused (never `display: none`), and targets `<main id="main" tabindex="-1">` so focus really moves.
**Detect.** `outline: none` / `outline: 0` without a `:focus-visible` replacement; rings drawn only with `box-shadow`; `tabindex` > 0; CSS reordering (`order`, `flex-direction: row-reverse`, grid placement, absolute positioning) that changes the visual sequence of interactive items; skip links hidden with `display: none`; sticky headers without `scroll-padding-top`.
**Fix.**
```css
:focus-visible { outline: 2px solid var(--color-focus); outline-offset: 2px; }
```

### INT-2 · Real elements, real keyboard (P0)
**Applies to.** every interactive element and custom widget (always check).
**Rule.** Clickable things are `<button>` or `<a href>`, not `<div onClick>`. Custom widgets carry the right roles and states (`aria-expanded`, `aria-controls`, `aria-selected`, `aria-checked`, `aria-haspopup`) and keys: Enter/Space activate, arrows move within composite widgets (menus, tabs, listboxes, radio groups, grids), Home/End jump, Escape closes one level.
**Detect.** `onClick` on non-interactive elements without role and key handlers; accordions with `<div>` headers; menus that ignore arrow keys.

### INT-3 · Pick the overlay by one question: does it block? (P1)
**Applies to.** every overlay: modal, sheet, drawer, popover, tooltip.
**Rule.**
| Need | Overlay |
|---|---|
| Must be answered before anything else (critical or destructive decision) | Modal with full scrim, one decision |
| Contextual choice, filters or options on a phone | Bottom sheet |
| Small contextual menu or quick action | Popover anchored to its trigger |
| Navigation, settings or a secondary panel | Drawer from the edge |
| Passive hint | Tooltip |
For a task, ask one more question: does the user need to see the page while acting? Then it is a bottom sheet on phones and a side drawer on desktop (an address edit beside the order it belongs to); a modal is for a full stop such as an irreversible decision, with the consequence spelled out. A desktop drawer stays between 320 px and 40% of the viewport (`width: clamp(320px, <preferred>, 40vw)`): narrower breaks its form, wider turns it into a page that hides the list; below about 800 px viewport use the sheet. Never stack two sheets or drawers: navigate inside the one container (replace its content, add a back arrow, move focus to the new view's heading), so one swipe or Escape still closes everything. Modals hold short content: no forms longer than about three fields (a long form in a modal traps the user and is lost on an accidental dismiss; if one is unavoidable, guard dismissal with a discard prompt or keep a draft). Popovers stay narrow (about 200 px for menus and filter lists), flip and shift against the viewport, and become a sheet on small screens when their content grows. A tooltip is not a popover: it is non-interactive and appears on hover and focus (INT-7). Only modals trap focus; drawers and popovers close on Escape and outside click and return focus to their trigger, unless a drawer dims and blocks the page, in which case it gets modal semantics (INT-4). Modals for routine actions add friction; never stack modals.
**Detect.** Modals for settings tweaks or info; dialogs containing more than three inputs; popovers detached from their trigger or wider than their content needs; nested dialogs; a second sheet opened from a sheet; drawers with fixed widths under 320 px or over about 40vw.

### INT-4 · Dialogs manage focus (P0)
**Applies to.** modals and dialogs.
**Rule.** On open, focus moves into the dialog (first field, or the least destructive action in a confirmation); Tab and Shift+Tab wrap inside; Escape closes and returns focus to the element that opened it, or to a logical neighbour if that element is gone (a deleted row); the page behind is inert (the `inert` attribute, not just a blur or scrim) and does not scroll. Prefer native `<dialog>` with `showModal()` where possible. Label it with `aria-labelledby`; destructive confirmations use `role="alertdialog"`.
**Detect.** Custom modals without focus trap or return; background still scrollable or focusable.
**Fix.** Native `<dialog>` with `showModal()`; lock the page with `body:has(dialog:modal) { overflow: hidden; }`.

### INT-5 · Bottom sheets for thumbs (P1)
**Applies to.** mobile menus, action lists, filter and option panels, bottom sheets.
**Rule.** On phones, put frequent menus and contextual actions in the bottom third where the thumb rests, not in the top corners. Prefer a sheet to a full-screen modal for short tasks: the page stays visible behind a dimming scrim, so context is kept. Give it a few fixed snap points, each with a content role (about 15% peek with a one-line summary, 50% for the form, about 92% for long lists), never free resting heights: on release, project the position with the release velocity and spring to the nearest snap point. Dismiss when the downward velocity passes a threshold (roughly 0.5 to 1 px/ms) or the drag passes about 50% of the sheet, so a quick flick closes it and a slow short drag returns; distance alone makes the sheet feel stuck. Add a grabber handle; at full height, a downward drag first scrolls the sheet's content back to the top before it moves the sheet. While a modal sheet is open, lock page scroll and stop scroll chaining (`overscroll-behavior: contain` on the sheet's scroller), move focus in and return it to the trigger on close. Dragging is never the only way out: keep a close or Done button, Escape and scrim tap, and make the grabber a focusable button that cycles snap points. A persistent non-modal sheet (a mini player) neither traps focus nor locks scroll. Round only the top corners, respect `env(safe-area-inset-bottom)`, keep rows at least 44 px tall. On tablets and desktop use a popover or side panel instead.
**Detect.** Mobile menus and action lists anchored at the top corners; desktop dropdowns reused unchanged on phones; the page scrolling together with an open sheet; sheets whose only close path is a drag.

### INT-6 · Dropdowns and selects (P1)
**Applies to.** dropdowns, selects, comboboxes and menu buttons.
**Rule.** The trigger looks clickable at rest, not only on hover (a caret and a border with 3:1 contrast), has hover and `:focus-visible` states, and has a hit area at least 44 px tall (48 px in touch-first UI). Measure the space before opening: flip upward or sideways when the menu would clip, and cap its max-height to the room available with internal scroll, because sometimes neither side fits. Keyboard: Enter, Space or Alt+Down open; arrows move; Enter selects; Home/End and typed letters jump; Escape closes and returns focus to the trigger; Tab closes. Add a filter field once the list passes about 10 items (announce the result count politely and show a "No results" state) and virtualise it beyond about 100. Open in about 150 ms (120 to 200 ms) with ease-out and close a little faster; much shorter reads as a pop, 500 ms drags; open instantly under reduced motion. A value picker is a combobox with a listbox (`aria-expanded`, `aria-activedescendant`); an action list is a menu button (`aria-haspopup="menu"`, `role="menu"`). Prefer native `<select>` unless options need rich content or search.
**Detect.** Menus clipped by the viewport or an `overflow: hidden` parent; fixed `top: 100%` placement with no flip logic; triggers around 30 px tall; long unsearchable lists; open transitions of 300 ms or more.

### INT-7 · Tooltips are hints (P1)
**Applies to.** tooltips.
**Rule.** Appear after about 300 ms on hover (filters passes on the way elsewhere) and immediately on keyboard focus; once one tooltip is open, neighbouring triggers in the same toolbar show theirs at once. Point at the trigger with an arrow kept aligned after any shift, never cover the trigger itself, and flip or shift near viewport edges with a collision-aware positioner (Floating UI `flip`/`shift`/`arrow`, or CSS anchor positioning with `position-try-fallbacks`, centred with `position-area: bottom` or `justify-self: anchor-center`, since `left: anchor(center)` only puts the tooltip's left edge at the centre); dismiss on Escape, blur, outside tap, and when the pointer leaves both the trigger and the tooltip, with a close grace of about 100 ms so the pointer can cross the gap (WCAG 1.4.13); fade in over about 100 to 150 ms, opacity only under reduced motion; one short sentence, width capped around 300 px; when the control has a shortcut, the tooltip names the same key as the menu (CON-10). Never put essential information or interactive content in a tooltip; on touch there is no hover, so the information needs another home, for example a toggletip opened by tapping an "i" button. Use `role="tooltip"` referenced by `aria-describedby`.
**Detect.** Tooltips with paragraphs or links; tooltips only on hover (not focus); icon-only buttons whose only label is a hover tooltip (they also need `aria-label`).

### INT-8 · Context menus measure first (P2)
**Applies to.** right-click and long-press context menus and their submenus.
**Rule.** Anchor at the cursor, but measure the menu against the viewport before showing it: below-right by default, flip up without room below, mirror left without room to the right, both in a corner; submenus also open leftward near the right edge. Group by intent with dividers (open, edit, share), keep related actions adjacent (Rename by Duplicate, Copy link by Share), and put the destructive action alone at the bottom in the danger colour plus an icon; a dozen flat items read as noise. Submenus stay open while the pointer travels diagonally toward them: a safe triangle from the cursor to the submenu's near edge, with a short timeout so a pointer that stops inside it still switches rows. Keyboard: arrows walk, typed letters jump, → opens a submenu, ← or Escape closes one level and puts focus back on the parent item, Enter/Space activates, Tab closes; Shift+F10 and the Menu key open the menu at the focused element. Shortcut hints sit right-aligned in the row. On touch, a long press (about 500 ms, with progress feedback and the native callout suppressed) opens the same actions in a bottom sheet headed by the item's name; also offer a visible ⋯ button, since right-click and long press are undiscoverable. Use `role="menu"`, `menuitem` and `separator`, with `aria-haspopup` and `aria-expanded` on submenu parents.
**Detect.** Menus placed at `clientX`/`clientY` with no measurement; Escape handlers that close the whole menu tree; `contextmenu` handlers with no touch or keyboard trigger; submenus closed on `mouseleave` of the parent row.

### INT-9 · Destructive actions use every signal (P0)
**Applies to.** delete, remove and discard buttons, their confirmation dialogs, settings danger zones, account deletion.
**Rule.** The button names verb and object ("Delete project" / "Keep project", not Yes/No), and the title and body say what is lost and for whom ("Q3 Campaign and its 84 assets, for everyone on the team"). The safe action owns the habitual primary position and the Enter default; the destructive button sits apart from it (which side varies by platform, the rule does not). Danger colour only for destruction, ideally one danger-coloured element per view, paired with an icon and the verb (VIS-6). Account- or data-level deletions live last in settings, in a bordered, titled "Danger zone" that says which actions are reversible (archive) and which are permanent (delete). Prefer undo (STA-14) for recoverable actions; for irreversible ones build the friction into the control: type the resource name; or hold to confirm with a visible progress ring that fires only on completion and cancels on release, pointer cancel or blur (at least 300 ms to filter taps, about 1 to 2 s for high-stakes actions), an accessible name that states the gesture and a keyboard or assistive-tech path; or a cancellable cooldown (for example 14 days before an account is deleted) that shows the exact final date and time zone, keeps a prominent "Cancel deletion" action and sends a notice with a cancel link. Confirmation dialogs use `role="alertdialog"`, put initial focus on the safe action, and treat Escape as the safe action.
**Detect.** "Are you sure?" with Yes/No; delete in the primary button slot or bound to Enter; danger colour on logout, badges, banners, tabs or toggles; destructive settings mixed in with routine ones; one-click irreversible actions; hold buttons that fire on press start.

### INT-10 · Buttons feel alive (P1)
**Applies to.** buttons, including submit buttons while their request runs.
**Rule.** Every button has hover (where hover exists), pressed, focus, busy and, if truly needed, unavailable states. Press feedback within 100 ms (MOT-3). Primary is filled, secondary outline or ghost, tertiary a text link; one primary per view or form. On lively products a small press squash and release spring, or a ripple from the press point, make the control feel physical: hover scale about 1.02 to 1.05 with a deeper shadow (scoped to `(hover: hover) and (pointer: fine)`), press about 0.95 to 0.97 with the shadow moving in, a slight overshoot on release, and a ripple that starts at the pointer coordinates, not the centre. On full-width or very wide buttons a 5% scale moves the edges several pixels, so change fill or brightness instead. On crisp products a fast value change is enough. Never linear easing; reduced motion keeps an instant colour or shadow change. The primary button's weight comes from a few deliberate properties: a solid accent fill with a 4.5:1 label, horizontal padding about two to three times the vertical, a semibold label, a radius from the scale, at least 44 px tall on touch, and optionally a soft shadow tinted from its own fill at low alpha, tuned per theme. Busy is not disabled: while the request runs the button keeps focus and its place in the tab order, swaps its label for a progress verb with a spinner ("Creating…"), ignores repeat clicks in the handler, and announces the outcome in a polite live region (`aria-busy` alone is poorly supported). Irreversible submits such as payments stay pending until the server confirms, then show the server's values (STA-4). For unavailable buttons see FRM-4.
**Detect.** Buttons with no `:hover`/`:active` styles; several primaries side by side; two equal-weight CTAs; `disabled={isLoading}` or `disabled={isSubmitting}`.

### INT-11 · Targets are big enough and close (P0 below 24 × 24 px, P1 below 44 × 44 px on touch)
**Applies to.** every interactive target on touch screens.
**Rule.** Interactive targets at least 44 × 44 px on touch and never below 24 × 24 px anywhere (WCAG 2.2 AA), even when the glyph is smaller; pad the hit area, keep the icon small (a 20 px icon in a 44 px box), preferably with `min-width`/`min-height` or a pseudo-element rather than padding that only works for one icon size, and without letting neighbouring hit areas overlap. Put frequent targets near where the pointer or thumb already is: primary mobile actions at the bottom, menus at the cursor, edit in place rather than in a far modal. Use `@media (pointer: coarse)` to grow controls for touch. Screen edges and corners are effectively infinite targets for a mouse. A floating action button is for the one main creation action per screen, with bottom padding on the content so it never covers the last row or its actions; bottom-docked CTAs clear `env(safe-area-inset-bottom)` (INT-27).
**Detect.** 16 to 32 px icon buttons without padding on mobile; tiny close buttons; primary mobile actions at the top of the screen.

### INT-12 · Hover is an extra, never the only path (P0)
**Applies to.** anything revealed or triggered on hover: card actions, row actions, hover menus.
**Rule.** Touch has no hover: the browser turns the first tap into a sticky `:hover` that can stay until the user taps elsewhere, so the tap is spent and the action never fires. Ask the input, not the device: gate hover-reveal styles with `@media (hover: hover) and (pointer: fine)` (consider `any-hover` for hybrids), never with user-agent or screen-width sniffing. Keep actions visible by default and hide them only inside that query, revealing on `:hover` and `:focus-within`; hide with `visibility: hidden` or `pointer-events: none` as well, because `opacity: 0` alone leaves invisible targets that still take taps and focus. Hover may reveal extras (compare, quick view), never the primary action, and every extra also has a touch home: in the card, behind a swipe that has a visible alternative, or in a sheet.
**Detect.** `opacity: 0` actions revealed only on `:hover`; `isMobile` or user-agent checks deciding what to show; `mouseenter` handlers with no touch or focus equivalent.

### INT-13 · Drag and drop says where things land (P1)
**Applies to.** drag and drop, reordering, kanban boards, free canvases.
**Rule.** Show `cursor: grab` on draggables and `grabbing` while dragging. On pickup the item lifts at once with redundant cues (scale about 1.03, a deeper shadow, a tilt of about 3°, applied to the drag preview only, not the original) and separates from its surroundings (dim the rest); a placeholder holds its origin so the layout does not jump, and siblings animate to make room. Valid drop targets answer before release, with a cue shaped like the result: in a list of cards, a dashed slot at the dragged item's measured height that opens once while the user aims, so nothing moves on drop (a thin insertion line there makes every card below jump at release); an insertion line is fine in dense text lists; a fill highlight for a whole container. While dragging, a closed folder or collapsed group springs open after hovering about 600 ms with a visible timer, cancelled when the pointer leaves. Structured surfaces snap to visible slots; free canvases do not. Escape cancels and returns the item to its origin. Every drop gets an undo toast naming the result ("Moved to Done") for about 5 s with a visible countdown, paused while hovered or focused. Provide a single-pointer and keyboard alternative (a "Move to…" menu or move buttons; Space/Enter to pick up, arrows to move, Space/Enter to drop) and announce pickup, position and drop in a live region. On touch, start the drag after a long press so scrolling still works, and auto-scroll near edges. Under reduced motion drop the tilt and scale, keep the shadow or outline. For file drops see FRM-16. While dragging, cover iframes and embeds with an overlay so they do not swallow the pointer.
**Detect.** Drag with no drop indication; no undo; drag as the only way to reorder; reliance on deprecated `aria-grabbed`/`aria-dropeffect`; no live-region announcements.

### INT-14 · Swipe actions are discoverable and safe (P1)
**Applies to.** swipeable list rows (mail, messages, tasks).
**Rule.** Every swipe has two thresholds: a short pull reveals action buttons and fires nothing; pulling past a clear commit line (often about half the row width, or a fast fling) fires the primary action on release, never on crossing, so dragging back cancels. Before the commit line the row resists like a rubber band, moving less than the finger; at the line the resistance ends, the icon pops and one haptic tick fires (re-armed if the user drags back). Keep direction meaning identical on every list; by convention swipe right is safe and reversible (archive, mark as read) and swipe left destructive, with the destructive action at the outer edge where a full swipe lands, and at most two actions per side. Teach the gesture once: on first launch the first row peeks its actions and settles back, then never again (under reduced motion use a static hint). A full destructive swipe needs no dialog but gets an undo toast (about 5 s, paused while touched or focused) with the real delete deferred until it closes. Colour by consequence, danger only for destruction. Every swipe action also exists as a visible button or menu item and as a screen-reader custom action.
**Detect.** Swipe-only delete; actions that fire when the threshold is crossed instead of on release; full swipe deleting with no undo; inconsistent directions across lists; more than two actions per side.

### INT-15 · Pull to refresh (P2)
**Applies to.** pull to refresh.
**Rule.** Prefer the platform control (`UIRefreshControl`, `SwipeRefreshLayout`, Compose `pullToRefresh`); a custom one makes the same six decisions. Refresh fires only on release past a visible threshold; released short, the list snaps back and nothing loads. The drag resists: content travels about half the finger distance, less as the pull grows (a rubber-band curve), because a 1:1 drag reads as ordinary scrolling. The pull indicator fills with distance, completes at the threshold and becomes the spinner itself, never a second loader. At the threshold, while the finger is still down, one haptic tick (with the completed ring as the visual equivalent, since web haptics are unreliable) confirms the commit; dragging back disarms it. On release the list settles with a slight overshoot (none under reduced motion, and a non-rotating indicator), stays scrollable during the reload and inserts new rows in place with a brief highlight; if the user has scrolled away, keep the scroll anchor stable and show a "1 new" pill instead of jumping. On the web, `overscroll-behavior-y: contain` stops the browser's own pull-to-refresh from competing. The gesture is hidden, so also offer a visible refresh action (button, menu item or custom accessibility action) and announce "Refreshing" and "Updated, 1 new" politely.
**Detect.** Refresh triggered during the drag or on any short pull; 1:1 pull translation; a separate spinner swapped in on release; scroll locked or the list blanked while refreshing; no non-gesture refresh path.

### INT-16 · Navigation by platform and depth (P1)
**Applies to.** app shells, site headers, sidebars, bottom tab bars, hamburger menus, breadcrumbs.
**Rule.** Choose by width and depth. Phone: a bottom tab bar with 3 to 5 top destinations, icon plus visible label, always visible, at least 44 px targets above the bottom safe area; beyond five, add a "More" destination. Medium widths: a navigation rail. Desktop: a persistent sidebar for 5+ sections or hierarchical content, expanded by default; people may collapse it to an icon rail, never to nothing. A hamburger holds only secondary items (settings, account, billing, help, sign-out), never primary destinations, least of all on desktop, because hidden navigation is used markedly less. The command palette (Cmd+K on macOS, Ctrl+K elsewhere) is an advertised accelerator next to visible navigation, never instead of it: new users do not know it exists. Breadcrumbs only when the hierarchy is deeper than two levels (INT-28). Wrap each navigation region in a labelled `<nav>`, mark the current location with `aria-current="page"`, and build app tab bars from links, not `role="tablist"`. Order matters: first and last slots are remembered best (CON-4).
**Detect.** Primary navigation hidden in a hamburger; collapsed-by-default desktop sidebars; bottom bars with six or more items or icon-only items; breadcrumbs on flat sites; app tab bars marked up as `role="tablist"`.

### INT-17 · Tabs are a system (P1)
**Applies to.** in-page tabs and their mobile replacements (segmented controls, section pickers).
**Rule.** The indicator slides to the new tab in about 250 to 300 ms with ease-out or a light spring (for example damping 22, stiffness 200), never a 0 ms jump (MOT-11). Overflow stays on one row: horizontal scroll, edge fades only on the side that has more, chevron buttons on pointer devices, the active tab scrolled into view; never wrap to two rows. Keyboard: roving tabindex, arrows move between tabs, Home/End jump to first and last, Tab leaves the tab list into the panel; activate on arrow for cheap panels, on Enter/Space for panels that load data. Focus and active use different properties (an outline ring vs an underline or fill), not just different hues. Content changes as one motion with the indicator: a short fade out, a brief gap, a fade in (about 80 ms each, or a 150 to 200 ms crossfade) that never blocks input, with the container height interpolated so the page below does not jump; under reduced motion switch instantly. On mobile: a segmented control (radio-group semantics) for up to 4 options, a picker that names the current section and opens a sheet for 5 or more, never a squeezed desktop bar; targets at least 44 px. Use `role="tablist"`/`tab`/`tabpanel` with `aria-selected`, `aria-controls` and `aria-labelledby`.
**Detect.** Indicator moved by a class swap with no transition; `flex-wrap: wrap` on a tab row; focus and active styled identically; the desktop tab bar rendered unchanged on phones.

### INT-18 · Accordions and disclosures (P2)
**Applies to.** accordions, disclosures, FAQ lists.
**Rule.** The header is a `<button>` inside a heading, with `aria-expanded` and `aria-controls` pointing at the panel; Enter and Space toggle. Animate the panel with grid rows `0fr` to `1fr` (child `min-height: 0; overflow: hidden`) or to a measured `scrollHeight` in px, never `height: auto` (MOT-8; `interpolate-size` only as progressive enhancement). The chevron shares the panel's duration and easing token and starts in the same frame; a few frames of lag reads as broken (MOT-7). Collapsed content is `hidden` or `inert`, not merely zero height. Single-open for sequential steps, multi-open for FAQs. When an item low in a scroll container expands, keep the clicked header at the same screen position (record its top, correct `scrollTop` after layout) and fade the revealed content in just after the height starts. Under reduced motion drop the height animation and keep the chevron's state change. `<details>`/`<summary>` is a valid native choice (`name` makes a group exclusive).
**Detect.** `transition: height` towards `height: auto`; chevron and panel with different durations or delays; links inside collapsed panels still reachable by Tab.

### INT-19 · Resizable panels (P2)
**Applies to.** split views and resizable panels.
**Rule.** A 1 px visible divider with a wider invisible grab area (about 12 px for a mouse, at least 24 px under `pointer: coarse`), highlighted on hover, drag and `:focus-visible` at 3:1. Width is clamped between an explicit minimum and maximum (for example 240 to 640 px for a sidebar, with a cue when a limit is hit), and clamp and snap are designed together: below a snap threshold near the edge the panel collapses fully to 0 instead of resting as an unusable sliver, and the collapsed panel keeps a visible, focusable way to reopen it. Drag with Pointer Events and `setPointerCapture`; while dragging, put a transparent full-viewport overlay above iframes and embeds, set the resize cursor on `body` (not only the handle, or it flickers), and disable text selection, removing all three on `pointerup` and `pointercancel`. Keyboard: a focusable `role="separator"` with `aria-orientation`, `aria-valuenow`/`aria-valuemin`/`aria-valuemax`, `aria-controls` and a name ("Resize sidebar"); arrows resize in steps, Home/End jump to the limits, Enter toggles collapse. Offer a single-pointer alternative too (a collapse button or preset widths, WCAG 2.5.7). Persist the width per user and the collapsed state separately, so reopening returns to the user's width, and re-clamp on restore against the current viewport.
**Detect.** A grab area as thin as the 1 px line; widths that can reach 0 with no way back; a panel left at a sliver width; `cursor: col-resize` only on the handle; no overlay over iframes during drag; width reset on reload; a separator that is not focusable.

### INT-20 · Collaborative presence (P2)
**Applies to.** real-time collaborative surfaces: remote cursors, avatar stacks, selection locks, follow mode.
**Rule.** Remote cursors arrive about 10 times a second; draw them at display rate by interpolating between the last two points (about one tick behind) so they glide instead of teleporting, never smooth the local cursor, throttle outgoing updates and fade idle cursors. Colour each person from a stable hash of an internal user ID (not the email), mapped to a fixed set of the project's tokens on which the name label keeps 4.5:1, so the same person has the same colour every session; colour is never the only identifier (keep name labels and initials). Show presence before anyone acts, in a fixed place: an avatar stack of about three faces plus a "+N" button that lists everyone, and an online count. When someone selects an element, outline and badge it in their colour and lock it; others see "<Name> is editing" instead of silently ignored clicks, and locks release on deselect, disconnect or timeout. Offer "follow" from an avatar, framed in that person's colour with a "Following <Name>" label; any local pan, zoom or Escape exits, and under reduced motion the followed viewport snaps rather than animating.
**Detect.** Cursor positions applied straight from socket messages; colours from `Math.random()` per session; locks with no timeout or release on disconnect.

### INT-21 · Colour pickers are decision tools (P2)
**Applies to.** colour pickers.
**Rule.** Show OKLCH (or HSL) next to hex so lightness and hue can be adjusted predictably; remember recent picks; show live contrast against the intended background; preview transparency on light and dark; generate a tint/shade scale from one pick.

### INT-22 · Let CSS read DOM state (P2)
**Applies to.** styles that mirror DOM state through JavaScript class toggles; scroll locks set in effects; layout or density variants chosen in JavaScript.
**Rule.** When the state already lives in the DOM (checked, invalid, open, a child present, a child count), put one `:has()` rule on the container instead of mirroring it into framework state, handlers and cleanup effects: `.plan:has(:checked)` for a selected card; `.field:has(:user-invalid)` to switch border, label and icon to the error role together (`:user-invalid` waits for interaction, `:invalid` paints untouched fields); `.layout:has(> aside)` for a sidebar column; `.grid:has(> :nth-child(n + 5))` for compact density at five or more children (the `>` stops nested elements counting); `body:has(dialog:modal)` for scroll lock and dimming (not `dialog[open]`, which also matches non-modal dialogs; add `scrollbar-gutter: stable` so the page does not shift). Styling is not announcement: still set `aria-invalid` and link the message with `aria-describedby`. Never block submit with `form:has(:user-invalid) button { pointer-events: none }`: it hides the reason, Enter still submits, and the faded label fails contrast (FRM-4). `:has()` is Baseline since late 2023 and `:user-invalid` arrived separately; keep a fallback where old browsers matter.
**Detect.** `useState` used only to toggle a class from a checkbox or validity; `useEffect` cleanups restoring `body.style.overflow`; `items.length > N ? "compact" : "wide"`.

### INT-23 · Ask for permissions in context, once (P1)
**Applies to.** requests for notifications, camera, microphone, location, contacts or photos, on mobile and the web (`Notification.requestPermission()`, `getUserMedia()`, geolocation).
**Rule.** Ask only right after the user starts the feature that needs the permission (after saving a reminder, on tapping Scan), never at launch or on page load, and one permission at a time. When the system dialog is one-shot (iOS shows it once per install; Android treats two denials as "don't ask again"), first show your own card with the concrete benefit in the user's terms ("Get a reminder at 8 pm", optionally a preview of the notification) and a real "Not now"; call the system API only after the card's positive button. A "Not now" on your card costs nothing: wait for the next relevant intent rather than re-showing it every launch. The system dialog's purpose string is specific ("To scan your medication box"). Model the state explicitly (not determined, denied, granted) and re-check it when the app returns to the foreground. After a denial keep the feature visible but disabled, with the reason beside it on a focusable element and a direct link to the app's settings page ("Notifications are off · Open Settings"). Never style your card like the system dialog or make "Allow" the only way forward.
**Detect.** Permission requests in app start-up, `useEffect` on mount or page load; several requests in a row; generic copy ("We'd like to send you notifications"); re-calling the request API after a denial; features removed or silently broken when permission is denied; no settings link.

### INT-24 · Tree views: indent, guides, one rotating chevron, keyboard (P2)
**Applies to.** tree views: file and folder trees, nested navigation, outline and hierarchy panels.
**Rule.** Indent each level by about 16 px (`padding-inline-start: calc(var(--level) * 16px)`, so it mirrors in RTL) and draw a 1 px guide line under every open folder at its chevron's position, highlighting the guide of the hovered or focused branch; 8 px without guides cannot be read at four levels. Open and close by rotating one chevron 90° (about 180 ms ease-out, instant under reduced motion; it points left when closed in RTL), never by swapping two glyphs, and never change the folder icon. Keyboard per the WAI-ARIA tree pattern: one tab stop with roving `tabindex`; Down/Up move between visible rows; Right opens a closed node or moves to its first child; Left closes an open node or moves to its parent; Home/End, Enter to activate, type-ahead. Semantics: `role="tree"` with a label, `treeitem`, children in `role="group"`, `aria-expanded` only on nodes with children, and `aria-level`, `aria-setsize`, `aria-posinset` when lazily loaded or virtualised. Load a large folder's children on first open with skeleton rows inside that folder only (after a short delay, with `aria-busy` on its group), keep the rest of the tree usable, and show failures inline with retry. The row or at least 24 px is the chevron's hit area. Dragging into a tree follows INT-13, including spring-loaded folders, and every move also exists as a "Move to…" or cut and paste.
**Detect.** Indent under about 12 px with no guide lines; `{open ? <ChevronDown/> : <ChevronRight/>}`; a tree with no arrow-key handling; one spinner over the whole panel while one folder loads; `aria-expanded` on leaf files.

### INT-25 · Hold-to-record shows its state beyond the thumb (P1)
**Applies to.** press-and-hold controls with several outcomes: voice message recorders, hold-to-talk buttons, and their playback bubbles.
**Rule.** On the same frame as the press, confirm recording where the thumb does not cover it: a running timer in the input row and a button that swells past the finger, plus a haptic tick. The release has two outcomes, so show the current one continuously: a fixed cancel line on the horizontal drag, before it "Release to send", past it a delete icon and "Release to delete"; dragging back disarms. Sliding up locks a long recording and replaces the gesture with explicit Stop and Send buttons. Show a live input waveform and, after about 2 s of flat input, warn that the mic looks muted with the fix (Unmute, or the permission, INT-23). Every gesture has a single-pointer alternative (tap to start and stop with visible Cancel, Lock and Send; WCAG 2.5.1, 2.5.7) and announcements ("Recording started", "Release to delete", "Locked"). The received message shows its length, a scrubbable waveform (`role="slider"` with `aria-valuetext` such as "0:45 of 1:24"), elapsed or remaining time adjusted for speed, and a speed toggle (1x, 1.5x); under reduced motion the bars stay static with a progress fill.
**Detect.** Recording feedback only under the finger; release always sends; no cancel or lock; no level meter or silence warning; gesture-only recording; voice bubbles without length or seeking.

### INT-26 · Boards show limits and the whole flow (P2)
**Applies to.** kanban and other column boards.
**Rule.** Card dragging follows INT-13 (lifted preview, measured slot, keyboard and "Move to…" alternative). Show work-in-progress limits on the column header as text ("In progress 3 / 4"), change the header's state at the limit with a text or icon cue as well as colour, and refuse or warn on an over-limit drop with the reason ("WIP limit reached: finish one first"), per the team's policy, never silently. Collapse rarely used columns into narrow vertical labels with counts ("Done 42") so the whole pipeline fits without sideways scrolling; a collapsed column is a button named with its count ("Expand Done, 42 cards") and `aria-expanded`. Split teams or priorities into swimlanes with per-lane counts on one board rather than a second board, so one item never has two statuses. On phones show one column at a time with a column picker or swipe.
**Detect.** WIP limits hidden in settings or not shown; boards that need horizontal scroll at desktop widths; the same items duplicated across boards; over-limit drops accepted silently.

### INT-27 · Phone layouts: no input zoom, safe areas, thumb actions (P1)
**Applies to.** mobile web layouts and responsive versions of desktop screens: form inputs, fixed bottom bars, row actions, tables shown on phones.
**Rule.** Form controls render at 16 px or larger on phones (`font-size: max(16px, 1rem)`), because iOS Safari zooms into any focused input below 16 px; never stop the zoom with `user-scalable=no` or `maximum-scale=1`, which breaks pinch zoom (WCAG 1.4.4). Fixed bottom bars and docked actions clear the home indicator: `viewport-fit=cover` in the viewport meta, then `padding-bottom: calc(<space> + env(safe-area-inset-bottom))`. Primary row actions become wide buttons at least 44 px tall with at least 8 px between neighbours; a bulk-action bar names the count ("Approve 2"). Tables become cards or keep only the key columns (DAT-6); a desktop layout scrolling sideways is never the only phone view.
**Detect.** Input font sizes below 16 px in mobile styles (`text-sm` on inputs); `user-scalable=no` or `maximum-scale=1`; fixed bottom bars without `env(safe-area-inset-bottom)`; `viewport-fit=cover` missing while safe-area insets are used; icon-size row actions on phones.

### INT-28 · Breadcrumbs show where the page sits (P2)
**Applies to.** breadcrumb trails, "back to parent" links, folded path menus.
**Rule.** A breadcrumb shows the page's place in the hierarchy, never the visit history. Every ancestor is a real link with visible hover and `:focus-visible` states; the last crumb is the current page as plain text, not styled as a link, carrying `aria-current="page"` and worded exactly like the page title, so the trail confirms where the user is. Keep the trail on one line: up to 4 items, and past that keep the first level, the direct parent and the current page and fold the run in between into one ellipsis button (a menu button named "Show hidden levels", with `aria-haspopup` and `aria-expanded`); never fold the first level away, since it names the section and is the most common way out. Mark it up as an ordered list in `<nav aria-label="Breadcrumb">`, with separators drawn by CSS or marked `aria-hidden="true"`; muted ancestor text still meets 4.5:1. On narrow screens replace the trail with one back link that names the parent ("← Back to Invoices"), at least 44 px tall.
**Detect.** The last crumb rendered as a link or in link style; a crumb label that differs from the `<h1>`; a leading ellipsis that hides the root; trails that wrap to a second line; separator characters read out between items; a full trail of tiny links on phones; crumbs built from navigation history.
