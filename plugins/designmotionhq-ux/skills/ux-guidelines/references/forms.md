# Forms and input

Forms are where users do work and where products lose them. Every field has states, every rule is visible before it is broken, and nothing the user typed is ever lost.

Severity: **P0** blocks, loses data or fails accessibility, **P1** friction, **P2** polish.

---

### FRM-1 · Six field states, designed explicitly (P1)
**Applies to.** text inputs, textareas, selects, and fields with async checks (username or email availability).
**Rule.** Every text field has default, focus, error, success, disabled and loading, each distinct by more than colour (icon, text, border weight). Focus is a solid ring with at least 3:1 contrast against adjacent colours, never a soft blurred glow. Error combines the danger colour, an icon in the field and a message that says what is wrong and how to fix it, with `aria-invalid="true"` and the message linked by `aria-describedby`. Success is confirmed inside the field (check plus short text), not in a toast elsewhere. Disabled is a flat neutral fill with muted text, `cursor: not-allowed` and the reason in the helper line, never just `opacity: 0.5`, which reads as loading; if the value must stay readable or focusable, use `readonly` or `aria-disabled` instead of `disabled`. Loading shows an in-field spinner with status text ("Checking availability…"); during a keystroke-level check keep the field editable (debounce the check, discard stale responses) and block only form submission while it is pending. Announce async results through a polite live region.
**Detect.** Inputs with only default and error styles; error shown only as a danger border; field-level success sent to a toast; `opacity: .5` as the disabled style; focus shown only by a blurred `box-shadow`; disabled and loading sharing one look; async checks with no pending state.
**Tip.** When the state already lives in the DOM, let CSS read it: `.field:has(:user-invalid)`, `form:has(:user-invalid) .submit-hint`.

### FRM-2 · Labels live outside the field (P0)
**Applies to.** every form control.
**Rule.** Every input has a persistent visible label (above or beside it) tied with `for`/`id` or wrapping. A placeholder is an example, not a label; it vanishes on typing. Helper text sits under the field and is linked with `aria-describedby`.
**Detect.** Inputs with `placeholder` but no `<label>`; labels not associated; floating labels that overlap typed text.

### FRM-3 · Validate on blur, then live (P1)
**Applies to.** forms with validation.
**Rule.** Do not validate on every keystroke (it flags a value before it is finished) and do not wait for submit (a wall of errors the user must scroll back to hunt). Validate a field when focus leaves it, keeping a neutral focus style while it is being typed. Once a field has shown an error, switch that field to live validation so the error clears the moment the value is fixed; raise a new error in that field only on its next blur. Confirm correct fields too (check plus short text), mainly where there are format rules, and never in a way that implies a server-side check has already passed. Do not raise "Required" when the user merely tabs through an empty, untouched field; leave that to submit. Submit still validates everything as a safety net: keep the button enabled, move focus to the first invalid field (or an error summary on long forms), and give every error text that matches the actual value. Exception: rule-based fields such as passwords show their checklist live while typing (FRM-5).
**Detect.** `onChange` validation showing errors from the first character; submit-only validation; errors that persist after the value is corrected; "Required" fired on blur of a pristine field; error borders with no message.

### FRM-4 · Keep submit live; explain what blocks it (P1)
**Applies to.** form submit buttons and any conditionally unavailable button.
**Rule.** Do not grey out submit until the form is valid. Disabled buttons leave the tab order, cannot show a tooltip, are usually too faint to read and never say why. Keep the button active, validate on click, highlight the blocking fields, move focus to the first one, and name the blocker in text. If a button must be unavailable, use `aria-disabled="true"` with a visible reason and ignore the activation in the handler, not `disabled` with silence.
**Detect.** `disabled={!isValid}`; disabled buttons with tooltips that never fire; low-contrast disabled labels.

### FRM-5 · Password fields coach, never punish (P1)
**Applies to.** password fields (sign-up, sign-in, change password), their requirement checklists, strength meters and show/hide toggles.
**Rule.** Score strength by guessability (a zxcvbn-style estimator plus a check against breached and common passwords), not by composition rules: a dictionary word with predictable substitutions ticks every checkbox and is still weak, and length beats symbols. Prefer a length minimum (about 15 characters when the password is the only factor, 8 with MFA) to character-class rules. Show any requirements before typing and tick each live, beside a segmented meter that names its level in words (Weak, Fair, Strong) as well as colour; link both with `aria-describedby` and announce changes politely, not on every keystroke. Add a show/hide toggle: a `<button type="button">` labelled "Show password" with `aria-pressed`, which swaps `type` and keeps focus and caret in the field. Never block paste. Support password managers (`autocomplete="new-password"` or `current-password`, plus `autocomplete="username"` on the identifier in the same form) so the platform can offer a generated password, the strongest path. Keep submit enabled and name unmet rules on click (FRM-4). Compute the meter client-side and never log the value.
**Detect.** Rules shown only after a failed submit; strength computed from regex character classes; meter levels shown by colour alone; `onPaste={e => e.preventDefault()}`; no reveal toggle, or one that is not a button; missing `autocomplete`; submit `disabled` until the checklist passes.

### FRM-6 · Masked inputs format as you type and store raw (P1)
**Applies to.** formatted inputs: card numbers, phones, dates, currency, IBANs, postal codes, codes.
**Rule.** Insert separators as the user types and keep the caret right after the character just typed (map the caret by its digit index; Backspace just after a separator deletes the preceding digit). Group card numbers by network, not a fixed 4-4-4-4 (15-digit Amex is 4-6-5; lengths run 13 to 19), and show the detected brand mark, with a text alternative, as soon as the leading digits identify it; take prefixes from a maintained IIN table or the payment provider's field. Stay neutral while typing and validate on blur (for cards: length for the detected network and the Luhn check) with a specific message. Clean pasted and autofilled values (strip spaces, dashes and other junk) and reformat them instead of rejecting them. Show formatted, store raw; for card numbers that means storing the provider's token and last four, never the full number unless you are PCI DSS compliant. Use `type="text"` with `inputmode="numeric"` and `autocomplete="cc-number"` for cards (never `type="number"`, which drops leading zeros), `type="tel"` with `autocomplete="tel"` for phones, and a `maxlength` that allows for the separators.
**Detect.** Caret jumping to the end after formatting; one grouping regex for every card brand; an error shown on an incomplete value while focus is still in the field; paste rejected for spaces or dashes; `type="number"` on card, phone or code fields; formatted strings sent to the API.

### FRM-7 · One-time codes are one string (P1)
**Applies to.** one-time code and verification inputs, their resend buttons.
**Rule.** Model the code as a single string and render the boxes as a view of it (or use one real input styled as slots). Paste or autofill into any box strips non-digits, truncates to the code length and fills every box; handle multi-character input events too, because iOS drops the whole autofilled code into the first box. Focus advances on each digit; Backspace on an empty box moves back and clears. Use `inputmode="numeric"` with `pattern="[0-9]*"` (not `type="number"`) and `autocomplete="one-time-code"` on the first or only input. Label the group ("Verification code") and name each box ("Digit 2 of 6"). Resend sits behind a visible 30 s countdown and announces when it is available again, not every second; the server rate-limits regardless. Auto-submit on the last digit is fine if a visible submit remains. A wrong code shows an error message (`role="alert"`) with a shake (a static error state under reduced motion), then clears and refocuses the first box; a right one locks every box into a verified state with a "Verified" label. Never fail silently.
**Detect.** An array of six independent inputs with separate state; paste only filling the first box; `type="number"` slots; resend with no cooldown; wrong-code feedback that is only motion or colour.

### FRM-8 · Long forms become steps grouped by meaning (P1)
**Applies to.** forms with more than about seven fields, checkouts, onboarding and sign-up wizards, steppers.
**Rule.** Past about seven fields, split into three to five steps grouped by context (Personal, Shipping, Payment, Review), not by field count; keep short forms on one page. Show one progress indicator (bar, numbered dots or step labels; labels say most about what is left) with the current step and an honest total, updated when a step becomes conditional. Validate inside each step, on blur and on Next, so a step-one error never first surfaces at the end; keep Next enabled and focus the first problem (FRM-4), or state beside a blocked Next why it is blocked. End with a Review step that summarises every entry with an edit link back to its step. Mark up the stepper as an ordered list with `aria-current="step"` and text such as "Step 2 of 4: Shipping", move focus to the new step's heading, and map steps to the URL so browser Back moves one step. Persist entered data across Back, refresh and accidental close, but never write CVC or full card numbers to client storage, and clear saved state after a successful submit.
**Detect.** Single-page forms with 12 or more fields; steps split every N fields; errors from step one only shown on the last step; state lost on Back or reload; payment fields in `localStorage` wizard state; browser Back leaving the wizard.

### FRM-9 · Group related fields with spacing (P2)
**Applies to.** forms with more than one group of fields.
**Rule.** Tight spacing within a group (about 12 px between related fields), clearly larger gaps between groups (about 32 to 40 px). Spacing does the grouping; borders and dividers become optional.
**Detect.** Uniform gaps between every field; dividers used where space would do.

### FRM-10 · One tap, one request (P0 for payments and creates, P1 otherwise)
**Applies to.** buttons that submit, create, pay or send.
**Rule.** On the first tap, mark the button busy (spinner in place, `aria-busy="true"`, width locked so the layout does not shift) and ignore further taps with an in-flight guard. Send an idempotency key so the server de-duplicates retries. Resolve on the button itself: a check with a specific success, or an error that says what happened ("Card declined, nothing was charged"). Return the button to its idle state when the response lands, never on a timer. Keep it focusable while busy (no `disabled`, see FRM-4).
**Detect.** Submit handlers without an in-flight flag; `setTimeout(() => setDisabled(false), 2000)`; buttons that shrink when the label becomes a spinner; payment endpoints without idempotency.

### FRM-11 · Autosave is a state machine (P0)
**Applies to.** autosave, drafts, save-status indicators, offline editing.
**Rule.** Debounce writes: restart a timer on every input and send one write after about 800 ms of silence, never per keystroke; add a max-wait flush so a long unbroken burst still saves. Drive the status indicator from explicit states (typing, saving, saved, offline, error), each shown with an icon and a word, and reach "saved" only from a confirmed server response; while offline show the pending count ("3 changes pending") instead of a stale "Saved". Queue edits in persistent local storage (IndexedDB) while offline, treat failed requests as offline because `navigator.onLine` can be wrong, and replay oldest first with visible progress. Send a version or ETag with each write so stale writes are rejected, then merge or warn; never let the last write win silently across tabs or users. Add a `beforeunload` guard (call `preventDefault()`; browsers show their own text) only while unsaved or queued changes exist, and guard in-app route changes separately. Announce status politely, and "Couldn't save" with a retry.
**Detect.** `onChange={save}` with no debounce; "Saved" set before the request resolves; an in-memory-only offline queue; writes without a version; a permanent `beforeunload` listener; no handling for offline or conflicts.

### FRM-12 · Settings match the apply model to the stakes (P1)
**Applies to.** settings and preferences screens, settings search, unsaved-changes save bars, danger zones.
**Rule.** Match the apply model to the blast radius: low-risk toggles apply instantly (optimistically, with an inline "Saved" announced politely and rollback on failure); identity and high-impact fields (email, password, billing) use a sticky save bar with Cancel and Save, where Cancel restores the last saved values and leaving with unsaved changes is guarded. When one page mixes both, label each section's model. Group by user task with a heading per group, not by data model; put advanced options behind one disclosure and split large products into tabs by job. With many settings, add search that filters, highlights the match, shows its path (Workspace › Email › Digest), says how many were hidden, opens the result on Enter and matches synonyms. Mark each changed value with an indicator that is not colour alone, show a modified count and offer a per-setting reset ("Reset Font size to default"). Wall off destructive actions in a labelled danger zone in the last position, limited to the roles allowed to use them and gated by typing the resource name (see INT-9).
**Detect.** Mixed apply models with no indication; one global Save for harmless toggles; identity fields that autosave; one long flat list ordered by schema; search results without their location; only "Reset all"; delete account as a single click.

### FRM-13 · Toggles look and behave like switches (P1)
**Applies to.** switches and toggles, including server-backed settings toggles.
**Rule.** A toggle is for an immediate on/off effect; use a checkbox when the change needs a Save. Proportions: track width about twice its height, knob diameter equal to track height minus twice the inset, the same inset on every side in both states (or the design system's switch token). Track colour, knob position (`transform`, never `left`), knob shadow and an on/off cue change together on one shared duration of about 250 ms, ease-out. State is never shown by colour alone (an on/off label or an icon in the knob), and the off-state track edge and the knob reach 3:1 against their surroundings. Keyboard: Space toggles; visible focus ring; `role="switch"` with `aria-checked` (or a native checkbox with `role="switch"`); the label text stays fixed. Keep the hit area at least 44 px even when the track is smaller. For async preferences: flip immediately, show progress inside the knob, ignore repeat taps while pending, and roll back with an announced explanation on failure; consequential settings (billing, security) confirm with the server first.
**Detect.** Toggles inside forms that also have a Save button; div-based switches without role or keyboard support; knobs animated with `left`; track, knob and label transitions on different durations; on/off shown only by track colour.

### FRM-14 · Date pickers lead with presets (P1)
**Applies to.** date and date-range pickers, date inputs.
**Rule.** Offer one-click relative presets first (Today, Yesterday, Last 7 days, Last 30 days, Last quarter) and Custom range last, and show the resolved dates of any choice in a summary with the day count; define "last N days" so it spans exactly N days. Custom range: the first click sets the start, hover (or the first tap on touch) previews the range, the second click sets the end, and both ends stay draggable, with a keyboard alternative. Show two months side by side for ranges, three on wide screens. Full keyboard per the APG date-picker pattern: arrows move by day and week, Home/End to the week's edges, Page Up/Down by month, Shift+Page Up/Down by year, Enter selects, Escape closes and returns focus to the trigger; always allow typing the date in the locale's order, parsed leniently and validated on blur or Enter. Give each day cell a full accessible name ("Monday, 5 May 2026, range start"); mark out-of-range dates unavailable rather than hiding them. On mobile, use a full-screen sheet with months scrolling vertically, a Today jump, cells of at least 44 px and a large confirm button in thumb reach, not a tiny popover.
**Detect.** Range selection that needs many "next month" clicks; a single-month range picker; presets without resolved dates; no typed entry, or a hardcoded MM/DD mask; desktop popover reused on phones.

### FRM-15 · Sliders design around finger imprecision (P1)
**Applies to.** sliders and range inputs, including two-thumb range filters.
**Rule.** Make the whole row (at least 44 px tall) the drag target, not a 4 px track: pressing anywhere moves the nearest thumb there and continues as a drag, with pointer capture and `touch-action: pan-y`. Fill the track to the thumb (between thumbs for a range) so length shows the value. Snap to steps when round values matter, with ticks that match the step. Float the current value above the thumb while dragging (not under the finger, clamped at the ends) and keep a persistent readout. For ranges, use two thumbs with a filled band, each its own focusable slider with its own label, kept min ≤ max. Prefer native `<input type="range">`; a custom one uses `role="slider"` with `aria-valuenow` and a formatted `aria-valuetext`. Keyboard: arrows one step, Page Up/Down a larger jump, Home and End to the extremes. Fill and focus ring reach 3:1 against the track. Offer a number input next to it when exact or wide-range values matter.
**Detect.** Bare 4 px tracks as the only hit area; free values like 47.3 where steps make sense; ticks that disagree with `step`; no value visible while dragging; one focus stop for two thumbs; no keyboard.

### FRM-16 · File upload is five signals (P1)
**Applies to.** file uploads and dropzones.
**Rule.** The dropzone reacts while a file hovers (border, highlight, copy change). Progress is honest: percent, time left, ideally rate. A failure gets inline retry that resumes rather than restarts. Success shows proof: thumbnail, name, type and size. In a queue each file has its own row, progress and retry, so one failure never blocks the rest. Validate type and size before uploading and say the limits up front.
**Detect.** A bare `<input type="file">`; one spinner for a multi-file upload; failed uploads that must start over.

### FRM-17 · Inline editing keeps every pixel (P2)
**Applies to.** click-to-edit text, titles and table cells.
**Rule.** Editable text hints its affordance on hover and focus (subtle background or pencil), shows the pencil persistently on touch, and is keyboard reachable with a name such as "Edit title". The input appears in exactly the same box with the same font, size, line-height and padding; reserve a transparent border in the display state so only its colour changes and nothing moves (zero layout shift). Entering edit mode focuses the input and selects its text. Enter commits (Cmd/Ctrl+Enter for multi-line), Escape cancels and restores the original, and focus returns to the text. Blur follows one rule app-wide (save or discard; pick one, and keep a recoverable draft if it discards). Save optimistically; on failure roll back, keep the draft, say why in an announced message, and ignore stale responses. Where a slip is expensive (invoice status, amounts), show read-only content with an explicit Edit action instead.
**Detect.** Display and edit states with different padding, line-height or border width; hover-only affordance; Escape that keeps the typed value; inconsistent blur behaviour; lost drafts on error.

### FRM-18 · Button labels name the outcome (P1)
**Applies to.** every button label.
**Rule.** Labels say what the user gets or what will happen ("Create my account", "Send invoice", "Delete project"), not the mechanism ("Submit", "OK", "Yes"). See CON-1 for microcopy.
